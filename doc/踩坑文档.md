## 坑 1：非 HTML 资源漏发 content-type，整站 CSS 被浏览器拒收

**这是最要命的一个。界面看起来"完全没有 CSS"，但代码里样式明明注入了。**

### 现象

- 用户在 Hana 卡片里看到的：裸 HTML，按钮是浏览器默认的白色方块，文字是默认字体
- 我在浏览器里直接打开代理端口：**一切正常**，配色、圆角、图标齐全
- 同样是那份 HTML，两边表现完全不同

### 根因

代理为了给 HTML 注入内容（主题、隐藏、base 垫片）后重算 `Content-Length`，
剥掉了一批响应头。代码长这样：

```js
if (lk === "content-encoding" || lk === "content-length" || lk === "content-type") continue;

if (!isHtml) {
  clientRes.writeHead(upRes.statusCode || 502, outHeaders);  // ← 直接发，content-type 没补回来
```

**注释里写着"非 HTML：原样流式透传"，但它并不是"原样"——`content-type` 已经在上面被剥掉了。**

而 magpie 的响应带：

```
X-Content-Type-Options: nosniff
```

浏览器规则很硬：**`nosniff` + 没有正确 MIME 的样式表 → 直接拒绝应用**。
于是 app.css / app.js 全被丢弃，页面退回裸 HTML。

### 当初怎么量出来的

直连代理拿一个 CSS，看响应头：

```
=== 直连代理 /app.css ===
状态: 200   ← 状态码完全正常，所以肉眼和普通检查都会放过
type: null  ← 真凶在这里：MIME 是空的
长度: 229015
```

再直连上游对比，确认上游是有 `content-type` 的（虽然回 401，但头在）：

```
=== magpie :49375/app.css ===
状态: 401
content-type: text/plain; charset=utf-8
x-content-type-options: nosniff   ← 就是它把空 MIME 变成了致命的
```

浏览器里再量一次，拿到决定性数字：

```
修复前：cssRules 总数 = 0 条     ← 一张样式表都没生效
修复后：cssRules 总数 = 2956 条
```

### 修法

1. **非 HTML 响应不再剥 `content-type` / `content-length` / `content-encoding`**，
   只对需要注入重算的 HTML 剥。
2. 补一张 **MIME 兜底表**（`mimeOf`）：上游不给 `content-type` 时按扩展名补上。
3. `isHtml` 判断加**路径兜底**：上游不给 HTML 页发 `content-type` 时，按路径识别
   （无扩展名或 `.html` 视为页面），否则会漏掉注入。

### 教训

> **「状态码 200」不等于「这个响应可用」。**
> 一个 200 的 CSS 响应，MIME 为空，在 nosniff 下等于一张废纸。

## 坑 2：隐藏功能的选择器瞄错了 DOM

**「藏掉 Library / Sessions」配置一直存在、也一直在注入，但就是不生效。**

### 现象

设置页打开了隐藏开关，注入的 `<style>` 也在 HTML 里（能看到 `#view-library` 这类规则），
但界面上的「会话」「资源库」两个 tab 纹丝不动。

### 根因

我照 magpie 源码里的**字符串**猜了选择器：

```js
library: ['#view-library', '#ptabs [data-ptab="library"]'],
```

真实的顶部导航是：

```html
<nav class="seg" id="nav">
  <button data-view="agents" class="on">Agents</button>
  ...
  <button data-view="sessions">Sessions</button>
  <button data-view="library">Library</button>
</nav>
```

`#ptabs` 是**另一个东西**——一个 `<nav class="ptabs" id="ptabs" hidden>`，
窄屏时才用的备用导航。我打的规则全打在一个隐藏元素上，自然毫无动静。

### 当初怎么量出来的

直接拉一份真实 HTML，把导航和所有 view 容器列出来：

```js
#nav 的按钮:        agents, providers, gateway, routing, usage, sessions, library, plugins
所有 view-* 容器:   view-agents, view-providers, ..., view-sessions, view-library, ...
id="ptabs" 容器:    <nav class="ptabs" id="ptabs" hidden>   ← hidden！
```

`hidden` 两个字就是全部答案。

### 修法

改用真实选择器：

```js
library: ['#nav button[data-view="library"]'],
sessions: ['#nav button[data-view="sessions"]'],
```

修完浏览器里实测：顶部导航从 8 项变成 6 项，「会话」「资源库」消失。

### 教训

> **不要从源码字符串猜 DOM。去量真实渲染出来的标记。**
> 这是同一个错误在一天里犯了两次（第一次是猜 CSS 变量名，第二次是猜选择器）。

## 坑 3：主题脚本自我引用，把 magpie 自己的颜色当成了宿主主题

**主题注入跑了，但取到的色号是 magpie 自己的默认深灰，不是 Hana 的青夜。**

### 现象

注入的脚本确实执行了（`#hana-theme` 存在、`data-theme` 也设上了），
但量到的变量全是 magpie 默认值：

```
--hana-bg: #1a1a1e   ← magpie 自己的深色
--accent:  #a5b4fc   ← magpie 自己的浅紫
```

而 Hana 的青夜主题是 `--bg: #3B4A54`（深青蓝）、`--accent: #C99AAF`（柔粉）。

### 根因

取值函数从 `window` **自己**起步向上找：

```js
function hostVars(){
  var w = window, i = 0;
  while (w && i < 6) {
    var cs = w.getComputedStyle(d.documentElement);   // ← 直接访问代理时，这就是 magpie 自己
    ...
    w = w.parent;
  }
}
```

直接访问代理时页面是顶层文档，`window.parent === window`。
于是它读到 magpie 自己的 CSS 变量，把 magpie 的默认色**当成宿主主题**又套了回去——一个闭环。

### 修法

**只从 `parent` 起向上找，跳过自己**：

```js
try { if (!w.parent || w.parent === w) return null; } catch (e) { return null; }
// 再从 parent 逐层向上
```

卡片里本页是挂在宿主源下的 iframe，`parent` 就是 Hana（同源可读）；
直接访问代理时 `parent` 就是自己，此时直接返回 `null`，走「按主题名取 CSS」的兜底路径。

### 教训

> **凡是「向上找宿主」的代码，都要显式排除自己。**
> `window.parent === window` 这个自反情况，是这类 bug 的固定入口。

## 坑 4：启动流程里的死锁——第一次明明成功，却被判 90 秒超时

**不是 magpie 起不来，是我的就绪检测认不出来。**

### 现象

日志里：

```
启动受管 runtime（attempt 1，代理端口 47768）
启动失败（第 1 次）：90s 内未就绪              ← 但其实起来了
启动失败（第 2 次）：已有活跃受管服务名 "magpie-ui"  ← 重试撞车
...
```

实测：第一次的端口（47768）**在监听**、返回 200，magpie 也在跑。
第一次就是成功的，是被误判了。

### 根因

查询状态的函数要求先有端口，而端口的赋值又在查询成功之后：

```js
async function proxyJson(path, init) {
  if (!state.proxyPort) throw new Error("代理未就绪");   // 要拿状态 → 得先有端口
  ...
}
// 而调用处：
const st = await proxyJson("/_hana/status");   // ← 第一步就抛
state.proxyPort = st.port || state.proxyPort;  // ← 永远到不了
```

异常还被 catch 吞掉（"代理未就绪"不含"上游/magpie"关键词，被当成"还没起来，继续等"），
于是空转满 90 秒。

### 修法

**端口本来就是我自己选的**（`41000 + random`），不需要等查询结果回报。
在 `runtime.start` 返回后当场赋值：

```js
state.runtimeId = rt?.runtimeId || rt?.id || null;
state.proxyPort = port;   // 自己选的值，当场就能确定
```

顺带加了 `releaseStaleRuntime()`：reload 时先主动释放旧 runtime，
避免新实例撞上尚未释放的服务名。

### 教训

> **轮询循环里，"还没好"和"我根本没在看"要能区分开。**
> 如果一个字段是自己决定的，就不要把它设计成需要外部回报才能确定。

## 坑 5：写死色号，等于假设用户永远不换主题

### 现象

第一版主题映射里，我硬编码了一套"深色蓝调"：

```js
bg: "#16171b", accent: "#6b7dff",   // 我自己想象的 Hana 观感
```

而用户真实主题（青夜）：

```css
[data-theme="midnight"] {
    --bg:     #3B4A54;   /* 深青蓝 */
    --accent: #C99AAF;   /* 柔粉 */
}
```

差得不是一点半点。**色号从根上就是错的，无论注入机制修得多好都白搭。**

### 修法

改成**运行时读真实主题**：注入客户端脚本，优先读宿主已生效的计算值，
退化时按主题名取 `/api/apps/theme.css?theme=<name>`。用户换任何主题都自动跟随。

关键点：宿主这个端点**无需认证即可访问**，实测：

```
GET /api/apps/theme.css?theme=midnight  →  200，2928 字节，含 --bg: #3B4A54
GET /api/apps/theme.css（不传）          →  200，47339 字节（默认暖纸主题）
```

### 教训

> **主题不是一个值，是一个会变的接口。写死任何色号都是在赌用户不换主题。**

## 坑 6：注入位置——样式排在它要覆盖的样式之前

### 现象

主题 CSS 和隐藏规则都注入了，但被 magpie 自己的样式压过去。

### 根因

我把注入块塞在 `<head>` 最前面：

```js
out = out.replace(/<head>/i, "<head>" + block);   // ← 排在 app.css 之前
```

实测位置：`hana-hide` 在 1278 字符处，而 `app.css` 在 1778 字符处。
同优先级下，**后出现的赢**，所以我那套被 magpie 的 `:root` 覆盖。

### 修法

1. 把主题 / 隐藏规则移到 `</head>` **之前**（app.css 之后）。
2. 用 `html:root{...}` 提升特异性，并给每个变量加 `!important`
   （实测 magpie 自己的变量定义**没有** `!important`，所以能压过）。
3. base 垫片仍必须在 `<head>` 最前——它要赶在 magpie 的脚本之前打补丁。
   所以现在是两段注入：**垫片在最前，主题与隐藏在最后。**

### 教训

> **注入不是"塞进去就行"，要问三个问题：塞在哪、和谁抢、谁赢。**

## 坑 7：以为需要剥前缀，其实是宿主已经剥过了（无害的空转）

这条不算 bug，但值得记——因为它展示了**怎么避免瞎猜**。

### 现象

我一度认为卡片里的静态资源请求会带宿主挂载前缀
（`/api/apps/magpie-hana/routes/_runtime/<rid>/app.css`），
于是写了个 `servicePath()` 把前缀剥掉再转发。

### 真相

给代理加了一个诊断端点后，直接看它**实际收到了什么**：

```
代理最近请求：
  200  /app.js?v=ed57d9e9818f        ← 本来就是根路径
  200  /library.js?v=0154f4d97cbc
  200  /api/state
  200  /icons/vscode.svg
```

**宿主自己就把前缀剥掉了**，转发给代理的已经是服务内路径。
那个 `servicePath()` 是个 no-op（无害，保留着兼容"宿主不剥"的情况）。

### 教训

> **与其推断请求长什么样，不如让服务把它收到的请求记下来。**
> 这次的 `/_hana/status` → `recent[]` 就是整个排查里最有用的一步。

## 坑 8：在代理层加压缩，让卡片里所有 CSS/JS 全部加载失败

**v0.3.0 引入、当天就被撞上。这是全篇最贵的一个坑，因为它在两条不同路径上表现完全不同。**

### 现象

- 卡片里：裸 HTML + 纯黑背景，按钮是浏览器默认样式（CSS 全丢）
- 代理日志：`/app.css`、`/app.js`、`/boot.js` … **全部 200**，看着完全正常
- 卡片内部探针报：`<LINK>` / `<SCRIPT>` 资源加载失败，一个不落

**同一个资源：代理说 200，浏览器说失败。**

### 根因

v0.3.0 为了提速，在代理里给文本资源加了 br / gzip：

```js
const enc = pickEncoding(clientReq, outHeaders["content-type"], ...);
if (enc) { outHeaders["content-encoding"] = enc; clientRes.end(compress(buf, enc)); }
```

而宿主的受管服务转发用的是 Node 的 `fetch()`：

```js
y.response = await fetch(f, { method, headers, ... });
const b = new Headers(y.response.headers);   // ← 原样保留 content-encoding
new Response(y.responseBody.body, { ... })   // ← 但 body 已被 fetch 解压
```

**`fetch()` 会自动解压 body，却保留 `content-encoding` 头。** 于是浏览器收到「明文 body + 声明是 br」——按 br 去解明文，失败，整个资源丢弃。

### 当初怎么量出来的

直接用 `fetch()` 对一个自己构造的 br 响应做对照实验：

```
测试服务器：原始 674B -> br 87B
fetch() 拿到的 Response：
  content-encoding: "br"     ← 头保留了
  content-length:   "87"     ← 还是压缩后的大小
  body 字节数:      698      ← 但 body 已经是明文
```

结论当场成立。真正的突破是给页面装了一个探针（`window.__hanaDiag`），
从 iframe 内部把「资源加载失败清单」发回代理的 `/_hana/diag`；
只靠外部看代理日志，永远只会看到一片 200。

### 修法

**代理一律不做压缩**，原样透传上游的 `content-encoding` / `content-length`。

代码里保留了一段长注释说明原因，并把 `pickEncoding` / `compress` 整个删除，
避免以后又有人（包括我自己）觉得「本地回环压一下能省七成」而加回来。

### 教训

> **中间层不要自己压缩，除非你能确认下游哪个环节会拆 `content-encoding`。**
> 自动解压 + 保留头，是这类 bug 最标准的配方。

> **「代理日志里全 200」不等于「浏览器拿到了」。**
> 这一条和坑 1（content-type）是同一个盲区：**状态码正常 ≠ 响应可用**。

### 顺带修正的一个认知

之前用 Node 测「压缩生效，省 73%」——那个数字**是假的**。
Node 的 `fetch` 同样自动解压，我量到的从来都是解压后的体积。
要量真实传输字节，必须用 `node:http` 直接发请求、自己不解压。

## 排查工具箱

### 1. 诊断端点 `GET /_hana/status`

代理内置，返回运行时全貌，其中 `recent[]` 是最近 30 条请求：

```json
{
  "phase": "ready",
  "upstreamPort": 32631,
  "requests": 57,
  "rewrites": 2,
  "recent": [
    { "url": "/api/apps/.../app.css", "path": "/app.css", "status": 200, "ct": "text/css" }
  ]
}
```

`url` 是**收到的原样**，`path` 是剥前缀后的，`ct` 是上游给的 content-type。
排查"请求到没到""MIME 对不对"一目了然。

### 2. 量，不要猜

```powershell
# 直连代理看响应头（MIME、nosniff 这类问题只有看头才能发现）
Invoke-WebRequest "http://127.0.0.1:<代理端口>/app.css" -UseBasicParsing | Select -Expand Headers
```

```js
// 浏览器里量渲染结果（这才是用户真正看到的）
Array.from(document.styleSheets).length                     // 样式表加载了几张
document.styleSheets[i].cssRules.length                     // 实际生效几条规则
getComputedStyle(document.documentElement).getPropertyValue('--bg')   // 变量真实取值
```

### 3. 三个必须分开验的层次

| 层次 | 验什么 | 怎么验 |
|---|---|---|
| 服务端 | 注入进去了吗、响应头对吗 | 直连代理，看 HTML 与响应头 |
| 浏览器 | 规则算不算得赢、样式生效了吗 | 开浏览器量 computed style / cssRules |
| 宿主卡片 | 在真实消费侧也一样吗 | **必须用户看，或自己进卡片环境** |

**这一整天最大的教训就是：我反复停在第 1 层就宣布修好，而问题在第 2、3 层。**

## 附：本次涉及的关键事实

| 项 | 值 |
|---|---|
| 宿主主题端点 | `/api/apps/theme.css?theme=<名>`（无需认证，实测 200） |
| 用户当前主题 | `midnight`（青夜），存在 `user/preferences.json` → `appearance.theme` |
| 青夜主题文件 | `{server}/desktop/dist-renderer/themes/midnight.css` |
| magpie 顶部导航 | `<nav class="seg" id="nav">`，按钮 `data-view="agents\|providers\|gateway\|routing\|usage\|sessions\|library\|plugins"` |
| magpie 窄屏导航 | `<nav class="ptabs" id="ptabs" hidden>`（**别拿它当目标**） |
| magpie 变量数 | `:root` 里 46 个，明暗两套 |
| magpie 的 nosniff | 上游响应带 `X-Content-Type-Options: nosniff` |
| 卡片挂载前缀 | 形如 `/api/apps/<id>/routes/_runtime/<rid>/_surface/<token>/`（token 很长） |
| 宿主转发实现 | `fetch()` + `new Headers(原响应头)` → **自动解压但保留 content-encoding** |
| 验证真实传输字节 | 必须用 `node:http` 发请求并自己不解压；Node 的 `fetch` 会骗你 |

## 最后：这三类坑的共性

1. **在我这侧跑得通，不等于在那边跑得通。** → 边界要单独验。
2. **从源码字符串猜行为，会猜错。** → 去量真实的 DOM / 响应 / 渲染结果。
3. **为一个目的加的代码，会伤到另一个目的。** → 剥 header 是为了重算 HTML 长度，
   却顺手毁掉了非 HTML 的 MIME。改公共代码时，要问"这个改动会影响哪些别的路径"。

## 补记：插件装不上（2026-10-07 夜）

**现象**：卡片里装 magpie 插件，toast 报 `npm 安装插件失败：downloading Bun 1.4.2 to run plugins: https://github.com/oven-sh/bun/releases/download…`；`GET /api/plugins` 里 `bun:false`，`settings.json` 里没有 `chinaMirror`（等于关）。

**两个根因，都不是「网络不好」这种糊话**：

### 1. 上游 30 秒超时掐死慢操作（本 App 自己的坑）

`runtime/proxy.mjs` 里写死 `upReq.setTimeout(30000)`。第一次装插件要先下 86MB 的 bun，那几分钟 magpie 一片安静，socket 空闲超时必然触发。实测：

```
POST /api/plugins/add  →  30.1s  →  503 {"ok":false,"error":"上游连接失败：上游超时"}
```

更糟的是这种超时原本还会走 `noteUpstreamFailure()`，攒够 6 次就把 magpie 杀掉重拉，正好掐在安装中途。

**修**：新增 `upstreamTimeoutFor(path)`。慢路径（`/api/plugins/add|remove|update|upgrade|check|mirror|search`、`/api/plugin-signin/`、`/api/update`）给 15 分钟，其余 3 分钟；超时记为 `upstream-timeout` 且**不**计入上游失败计数（慢不等于连不上）。

### 2. bun 的下载次序（不是缺文件，是次序）

magpie 自己会下 bun：`BunVersion=1.4.2`，带 SHA256 校验，落在 `<cache>/bun/<版本>/magpie-bun.exe`。次序是「官方源优先，失败才回退镜像」。国内网络下官方 GitHub 会卡很久：

| 「国内镜像」 | 第一次装插件耗时 |
|---|---|
| 开 | **11.1s** |
| 关 | 128.9s（官方卡住后回退 npmmirror，最终也成功） |

**结论**：不要手工往 `data/cache/bun` 里搬 bun - 那是单机偏方，别人用这个 App 时帮不上。正路是让用户开 magpie 插件页的「国内镜像」开关（`POST /api/plugins/mirror {"on":true}`，落在 `data/settings.json` 的 `chinaMirror`），App 的运行状态里已经显示它的开/关。

**验证**：删掉本地 bun，`POST /api/plugins/add {"spec":"@magpie-community/opencode-cline-auth"}`，镜像开 11.1s 装成、镜像关 128.9s 装成，两种情况 magpie 都自报 `bun:true / bunVersion:1.4.2`。测试插件已卸载，手工副本已删除（现在这份 bun 是 magpie 自己下的，SHA256 与用户原有的完全一致）。

**相关事实**：

| 项 | 值 |
|---|---|
| bun 落点（便携模式） | `<exeDir>/data/cache/bun/<版本>/magpie-bun.exe`（0.1.1103 的约定名带 `magpie-` 前缀，源码里是 `filepath.Join(bunDirOf(v), "magpie-"+bunExe())`） |
| bun 覆盖开关 | `MAGPIE_BUN=<path>` 直接生效，不做版本校验 |
| 镜像映射 | `github.com/oven-sh/bun/releases/download/bun-v<v>/<file>.zip` → `registry.npmmirror.com/-/binary/bun/bun-v<v>/<file>.zip`；npm 走 `BUN_CONFIG_REGISTRY=registry.npmmirror.com` |
| 查 bun / 镜像状态 | `GET /api/plugins` → `bun` / `bunVersion` / `mirror` / `plugins[]` |
| 装 / 卸 / 更新 / 开关 | `POST /api/plugins/{add,remove,update,upgrade,check}`（载荷 `{spec}`）；**是 `remove`，不是 `rm`**；`POST /api/plugins/mirror {"on":true}` |
| magpie 判便携 | exe 旁有 `data/` 目录（或 `.portable` 文件）→ 配置、缓存、插件全进 data，且「自己的东西一个字节都不写进用户目录」 |
| 插件目录 | `settings.Dir()/plugins` = `<配置根>/plugins/node_modules/<包>`，用 bun 装 |
| 系统代理 | 注册表 `ProxyEnable=1 / ProxyServer=127.0.0.1:7890`，环境里没有任何 `*_PROXY` 变量。**magpie 自己会读注册表代理**（`internal/netproxy/system_windows.go`），优先级是「设置里的 `proxy` → `*_PROXY` 环境变量 → 系统代理」，回环地址永不代理；插件（bun）拿到的代理是 magpie 主动递过去的（`netproxy.ForBun`）。这条早期写反了：Go 的 `http.DefaultTransport` 本身不读注册表，但 magpie 用 `netproxy.Install()` 换掉过它的 `Proxy` 函数 |

## 补记：卡片打开慢（2026-10-08）

### 现象

卡片打开时先转一会儿圈（页内骨架），不是「magpie 正在启动…」那张等待页（这句话很重要：两者根因完全不同）。

### 量出来的数字（改之前）

| 请求 | 耗时 | 说明 |
|---|---|---|
| 代理层转发开销 | 1~10ms | `/api/update?lang=zh` 全程 3ms |
| `/`（页面 HTML） | 8~11ms | 只有 app 刚启动那一次 68ms |
| **`/boot.js`** | **277~585ms** | **只有 81 字节**，却写在 `<head>` 里阻塞首绘 |
| `/api/settings` | 290~430ms | |
| `/api/state` | 350~485ms | |
| `/api/plugins` | 447~512ms | |
| `/api/providers` | 393ms | |
| `/api/library` | **1387ms** | 最贵的一条 |
| `/api/omarchy`（对照） | 1ms | 唯一不读设置的那条 |

### 排除了什么（免得下一个人白忙）

- **不是用户配置的锅**：复制一份 magpie.exe、空配置另起一个实例，同样是 `/boot.js` 277~313ms、`/api/settings` 290~301ms。
- **不是 Syncthing**：它只同步 `C:\Users\SSS\Sync` 和 `D:\Obsidian`，没碰 `.hanako`。
- **不是杀软**：Defender 实时防护 `False`、引擎 `0.0.0.0`（服务根本没在跑）。
- **不是文件被锁**：用和 Go 相同的共享标志（`ReadWrite | Delete`）读那个文件 400 次，平均 0.59ms。
- **不是我们的代理**：同一台机器上 `/api/update` 3ms、静态资源 1~4ms。

结论：是 magpie 自身的开销，且只落在「要读一遍设置」的处理器上。`settings.Load()` 的代码路径本身是微秒级的（`steady.ReadFile` + `Unmarshal` + 几个 if），而 `internal/steady` 在 Windows 上有个「读失败就 10ms 一次、最多 50 次」的重试（上限 0.5 秒），观测到的 277/411/438/481/508/585ms 正是这个形状 —— 但具体为什么每次读都要等，尚未钉死（没有 Go 工具链，取不到 pprof）。

### 为什么不能直接改 magpie

项目红线：不改 magpie 的源码与 exe。所以优化只能落在代理层。

### 修法（代理层，transparent）

1. **只读接口的短 TTL 缓存 + stale-while-revalidate**：白名单 6 条（`/boot.js` 60s，`/api/settings` 30s，`/api/state`、`/api/plugins`、`/api/providers`、`/api/library` 各 3s）。命中直接回；过期了也先回旧的，同时后台单飞刷新。
2. **写入即作废**：任何非 GET 一到，整张表清空，而且写之前、写之后各清一次（免得并发中的回源把旧值填回去）。所以自己动手改过的东西立刻能看到 —— 兜住正确性的是这一条，不是 TTL。
3. **ready 时预热**：上游一就绪就把这 6 条拉一遍，卡片第一次打开就是热的，不用拿冷缓存去撞那 400ms。
4. **带 `?v=<内容哈希>` 的 js/css 改发一年长缓存**：magpie 只发 `no-cache`，每次打开都要条件请求十几个文件、校验近 1MB；哈希即内容，改成 immutable 是安全的。

### 验收数据（同一台机器）

| 请求 | 改前 | 改后（缓存命中） |
|---|---|---|
| `/boot.js` | 393ms | 1~3ms |
| `/api/settings` | 365ms | 1ms |
| `/api/state` | 407ms | 1~2ms |
| `/api/plugins` | 512ms | 1~2ms |
| `/api/providers` | 393ms | 1~16ms |
| `/api/library` | 1387ms | 1~2ms |

另外核对过：缓存副本与同时刻回源**字节一致**（`/api/providers` 只有易变的额度字段值不同），首页注入（`hana-theme-seed` / `hana-hide`）都还在。

### 怎么关

- 关缓存：把 `CACHED_GETS` 清空（`new Map([...])` 里删条目即可，删光就等于没有这层）。
- 关长缓存：`USE_IMMUTABLE_ASSETS = false`。
- 看命中情况：`GET /_hana/status` 的 `cache` 字段（`hit` / `stale` / `miss` / `refresh` / `cleared` / `entries`），设置页的「运行状态」里也有一行。

### 教训

- 「首屏慢」先分清是**页面自己慢**还是**它在等一个慢请求**。这次是一个 81 字节的文件卡在 `<head>` 里，按字节算大概是全世界最贵的一行。
- 排因要按「能一票否决的」排：先复制一个新实例（一分钟排除全部用户数据），再看别的程序（同步盘、杀软），最后才回到代码。
