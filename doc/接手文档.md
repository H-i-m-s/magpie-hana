## 一、这个项目要做什么

把 [magpie](https://github.com/yetone/magpie)（yetone 写的多 agent 模型统一管理器）**包装成 Hana 的一个 v2 App**，让它变成 Hana 的一部分，而不是一个要单独打开的软件。

### 用户的原话与真实诉求

> 「每次都要新开个软件太麻烦了（或者说还要从托盘中打开这个软件）。所以我想精简一部分内容，深度整合进 hana。开启 hana 即调用了这个插件（而且也不会在托盘显示个图标，更不用再想着把 exe 放在哪打开）」

拆解成六条可验收的目标：

| # | 目标 | 验收方式 |
|---|---|---|
| G1 | 不再出现 magpie 的托盘图标 / 窗口 | 任务管理器里没有带界面的 magpie 进程 |
| G2 | Hana 启动 → magpie 自动就绪；Hana 关闭 → magpie 跟着停 | 开关 Hana，观察 3425 的存活 |
| G3 | 不用再惦记 exe 在哪 | exe 住在插件名下，用户不需要知道路径 |
| G4 | 在 Hana 里能看到 magpie 的界面，且**配色与 Hana 一致** | 视觉判断（用户拍板） |
| G5 | magpie 里用不上的功能要能隐藏 | 视觉判断 + DOM 检查 |
| G6 | 别人装上也能用，exe 随包走、装完即用，不现场下载 | 干净环境安装验证 |

### 用户明确排除的

- **不要无头后台守护**。「可控」是关键 —— 进程的开关必须握在 Hana 手里，不要一个开机自己冒出来、用户看不见也管不着的东西。
- **不自动更新 exe**（见红线 R6），更新节奏由用户掌握。
- **只发 Windows**。不做 macOS / Linux（原因见第四节）。

### 顺带澄清的两个概念

- magpie 的「插件」和 Hana 的「插件」是两回事。本项目是 **Hana 的 v2 App**，同时它内部**也可以装 magpie 的插件**（这两件事互不干扰）。
- 用户机器上现有的三个 magpie 插件（`opencode-qoder-auth` / `opencode-workbuddy-auth` / `opencode-zcode-auth`）是 **Qoder CN / WorkBuddy / ZCode 能用起来的真正原因**。它们住在 magpie 的配置目录里，与 Hana 无关。

## 二、magpie 是什么（已核实的事实）

### 源码与产物

| 项 | 值 |
|---|---|
| 源码（本地） | `D:\Agent\magpie\` |
| 源码远端 | `https://github.com/yetone/magpie.git` |
| 当前使用的 exe | `D:\windows功能文件夹\下载\magpie-windows-amd64.exe` |
| 实测版本 | `0.1.838`（`magpie --version`） |
| 许可证 | **MIT**，`Copyright (c) 2026 yetone` |
| exe 体积 | 35.1 MiB |
| zip 压缩后 | **13.7 MiB**（实测 39%，用时 0.8s） |
| PE Subsystem | **2 = GUI 子系统**（所以跑 serve/web 都不弹黑框） |

### 三种运行模式（关键）

**网关和 exe 是同一个东西，不是两个程序。** 托盘图标只是它的一种出场方式。

| 命令 | 窗口 | 托盘 | 网关 | 网页 | 自动更新 |
|---|---|---|---|---|---|
| `magpie` | ✓ | ✓ | ✓ | — | ✓ |
| `magpie tray` | — | ✓ | ✓ | — | ✓ |
| `magpie web` | — | — | ✓ | ✓(3430) | ✓ |
| `magpie serve` | — | — | ✓ | — | **✗** |

> **本项目选择 `magpie web`**，因为它一次给三样：网关 + 完整界面 + 自动更新，且无托盘无窗口。
> 详见第五节「为什么是 web 而不是 serve」。

### 端口与健康检查

- 网关：`127.0.0.1:3425`，`MAGPIE_ADDR` 可改
- 网页：`127.0.0.1:3430`（`magpie web --addr` 可改）
- `magpie healthcheck`：网关活着 → 退出码 0
- `magpie --version`：打印版本号（用来比对更新，**不要解析其它命令的文本输出**）

### 只有一个网关主人（重要）

- Windows 上 `reusePort` 是**空实现**，第二个 magpie **绑不上 3425 就直接放弃**。
- `serveGateway()` 写了礼让逻辑：发现 3425 已有 magpie 在服务 → **不抢，只提供界面**。
- 每 **15 秒**轮询一次，端口被释放后自动接手。

> 意味着：我们**不需要写抢端口的逻辑**。起 magpie web 是安全的。

### 网页鉴权

- `MAGPIE_WEB_KEY`（16+ 字符）可固定 key；否则每次运行随机生成
- 链接形如 `http://127.0.0.1:3430/?k=<key>`
- 拿到 key 后种 cookie：`SameSite=Lax`、`HttpOnly`
- **本地回环请求免 key**（这一点决定了我们的反代方案是安全的）

### 便携模式（本项目依赖）

只要 exe 旁边存在：

- 一个名为 `data` 的**文件夹**，或
- 一个名为 `.portable` 的**文件**

magpie 就**把所有自己的状态都写进 `data/`**，一点不碰用户目录（VS Code portable 同款行为）。

### 配置位置

| 模式 | 位置 |
|---|---|
| 默认（安装态） | `~/.config/magpie/`（`XDG_CONFIG_HOME` 可改） |
| 缓存 | `~/.cache/magpie/` |
| WebView2 profile（Windows） | `%APPDATA%\<exe名>`；便携时 `data/webview2` |
| **便携** | `<exe所在目录>/data/` |

`appdir` 的决策**基于启动时的 exe 路径**，更新时 exe 被移到旁边不影响。

> 用户当前用的是默认路径：`C:\Users\SSS\.config\magpie\`
> 里面有：`providers.json`（厂商+key）、`plugin-auth.json`（**三个订阅登录**）、
> `usage.jsonl`（用量流水）、`settings.json`、`plugins/node_modules/`（三个 npm 包）。

### 对外接口（按稳定性排序）

**稳定度从高到低 —— 我们只依赖前三层，绝不碰第四层。**

| 层 | 例子 | 用途 |
|---|---|---|
| HTTP JSON | `/v1/models`、`/v1/magpie/quotas`、`/v1/magpie/route`、`/v1/magpie/limit` | ✓ 首选 |
| CLI `--json` | `quota --json`、`sessions --json`、`plugins --json`、`accounts --json` | ✓ |
| 进程接口 | `--version`、`healthcheck`（退出码）、web 启动行 | ✓ |
| CLI 文本 | `ls`、`providers`、`models` | △ 给人看的，会随排版变 |
| 私有文件 | `~/.config/magpie/*.json` 的内部结构 | ✗ **禁止读** |

`/v1/models` 返回的每个模型带 `id`（形如 `provider/model`）、`display_name`、
`magpie_label`、`context_window`、`max_output_tokens`、`reasoning`、
`supported_reasoning_levels`、`native_endpoints`。

### 前端结构（用于主题注入与功能隐藏）

- 前端资源：`internal/gui/assets/`，被 `//go:embed assets` 打进 exe
- **全部用相对路径引用**（`<script src="app.js">`），API 调用走绝对路径 `/api/...`
- **零 WebSocket / 零 EventSource**（全量搜索确认），只有普通 HTTP 轮询
  → **反代层不需要处理长连接**，工作量大幅降低

**CSS 变量化（主题注入的基础）：**

- `app.css` 的 `:root` 里集中定义 **207 个 CSS 变量**
- 已有明暗两套：`:root[data-theme="dark"]`、`@media (prefers-color-scheme: dark)`
- 核心变量（覆盖这十几个就能改变整站配色）：
  `--bg` `--card` `--card-2` `--pill` `--line` `--fg` `--fg-2` `--muted` `--faint`
  `--accent` `--accent-soft` `--sel` `--green` `--red` `--amber` `--shadow` `--font`
- `theme.js` 支持 `?theme=dark` 查询参数，**第一帧绘制前生效**（不会闪白）

**DOM 结构（用于隐藏功能）：**

```
顶部 tab:   [data-ptab="agents" | "usage" | "stats" | "routing"]
主视图:      #view-agents #view-providers #view-gateway #view-routing
            #view-usage  #view-sessions  #view-library #view-plugins #view-settings
设置子页:    [data-set="general|usage|network|models|privacy|otel|sync|about"]
```

## 三、Hana 侧的约束（已实测，非推测）

### 目录：apps 只读，app-data 可写

抓取正在运行的沙箱进程命令行，白纸黑字：

```
--allow-fs-read  = C:\...\apps\comfyui-hana
--allow-fs-read  = C:\...\app-data\comfyui-hana
--allow-fs-write = C:\...\app-data\comfyui-hana        ← 只有这一个可写
```

官方文档（`APPS.md`）对应表述：

> `ctx.dataDir` 是 `{HANA_HOME}/app-data/{appId}`，**可写**，**卸载保留**。
> 没有 `ctx.pluginDir`：隔离后安装目录**只读**。

**推论（这是 exe 位置的唯一依据）：**

magpie 自更新时的动作是 `tmp := exe + ".new"` → `os.Rename(staged, exe)`，
**必须往自己 exe 旁边写文件**。所以：

- ❌ exe 放 `apps/{id}/` → 只读 → **自更新当场失败**
- ✓ exe 放 `app-data/{id}/` → 可写 + 卸载保留 → 正确

> 这一条与「用户会不会更新插件」无关，是硬约束。

### 进程生命周期：Hana 关就跟着关

App 用 `app/runtime.execute` 拉起的子进程活在 Hana 的沙箱 **job object** 里。

> job object 的特性：父进程死 → **整棵进程树被回收**。

所以「Hana 关 → magpie 停」**不需要任何额外机制**，是白送的。

（对比：`comfyui-hana` 恰恰相反，它用 Windows 计划任务让 ComfyUI **活过** Hana，
因为跑图不该因为关 Hana 而中断。本项目不做这件事。）

### 包体积限制

| 项 | 限制 |
|---|---|
| 本地打包器 | 256 MiB 压缩 / 512 MiB 解压 / 30000 entries |
| **Hana 市场** | **50 MiB**（压缩后） |

Windows 版 exe 压缩后 13.7 MiB → 宽裕。

### 卡片服务挂载（本项目要用的关键机制）

Hana ≥ **0.1023.0** 支持在卡片上声明：

```json
"service": { "id": "<stable-id>", "path": "<mount-path>" }
```

行为：

- 宿主经 `_runtime` 代理挂载 App 自己的受管服务
- **页面与 Hana 界面同源** → 跨源问题消失 → **cookie 问题一并消失**
- 宿主**不会改写**任意 HTML —— **但 App 自己的反代可以改**
- 需要 `app/runtime.execute`（native 还需 `app/runtime.native` + 网络声明）
- 服务必须在 stdout 打出约定的 `readyMarker` 才算就绪
- manifest 里只存逻辑标识 `{id, path}`，**绝不存端口 / runtimeId / 临时 URL**

> 本机 Hana 版本：**0.1059.0** ✓ 满足。

### 其它已知

- `HANA_HOME` = `C:\Users\SSS\.hanako`
- App 目录：`{HANA_HOME}/apps/{id}/`
- App 数据：`{HANA_HOME}/app-data/{id}/`
- 官方文档：`{HANA_HOME}/artifacts/server/<版本>/APPS.md` 与 `APPS_EN.md`

## 四、⚠️ 红线：绝对不能做的事

> 这份清单的存在理由：**用户当前就在用 magpie 和 Hana 对话**。
> 当前对话模型 = `workbuddy/deepseek-v4.1-flash`，provider = `magpie`，
> 由 PID 54156（`D:\windows功能文件夹\下载\magpie-windows-amd64.exe`，托盘版）在 3425 上服务。
> 任何一条踩了，用户的对话当场断。

| # | 禁止 | 原因 / 后果 |
|---|---|---|
| **R1** | **禁止在用户对话期间运行 `magpie update`** | 它会替换 exe 并重启进程 → 3425 中断 → 对话断 |
| **R2** | **禁止运行任何会写 Hana 配置的 magpie 命令**<br>如 `magpie hanako <模型>` | 会改写 `~/.hanako/agents/hanako/config.yaml`，把当前模型换掉 → 对话断 |
| **R3** | **禁止让两个 magpie 共用同一份配置目录** | `providers.json` 原子写、`usage.jsonl` 追加写、agent 配置直改。<br>并发写**不会立刻报错**，只会悄悄写乱。 |
| **R4** | **禁止占用或干扰 3425** | 用户当前对话依赖它 |
| **R5** | **禁止读写 `C:\Users\SSS\.config\magpie\`** | 这是用户**现役**配置。只读也不要做，避免误判。 |
| **R6** | **禁止自动覆盖已存在的 exe** | 见第六节「版本播种规则」——否则会造成降级事故 |
| **R7** | **禁止在任何测试中使用用户真实的 `HANA_HOME`** | 官方明确要求：测试不得用真实 HANA_HOME 作 fixture |

### 测试必须的隔离条件（四项全中才允许碰真的）

1. exe 复制到**临时目录**（不要用用户那只）
2. exe 旁边建 `data/` 文件夹 → 触发便携模式 → 不写 `~/.config/magpie`
3. 设**假的 `HANA_HOME`**（临时目录）→ 看不见用户真实的 Hana
4. **随机端口**（不用 3425 / 3430）

## 五、架构设计

### 为什么是 web 而不是 serve

`magpie serve` 看着更贴合「无头」，但它**没有自动更新**（`updates.start()` 只在 GUI 和 web 模式里调用，`serve` 里一行都没有）。
`magpie web` 一次给齐三样：

1. 网关（内部照样 `startBackend()`，与托盘版行为一致）
2. 完整网页界面（就是托盘版那个面板）
3. 自动更新

而且无托盘、无窗口、不弹黑框 —— 正是用户要的「进程可控但隐形」。

### 三层结构

```
Layer 1  托管层   （近乎零维护）
         找到 exe → 拉起 magpie web → 健康检查 → 停止 → 状态上报
         依赖：进程退出码 + --version + healthcheck

Layer 2  反代层   （本工程唯一有技术含量的部分）
         宿主 _runtime 代理 → 我们的反代 → magpie:3430
         职责：透传 + 改 HTML（注入主题、藏功能）+ 跟 Hana 主题

Layer 3  工具层   （低维护）
         magpie 工具：status / models / quotas / agents / use / start / stop / update
         数据一律走 HTTP JSON 与 --json
```

### 为什么需要反代（而不是裸 iframe）

裸 iframe 的致命伤：**跨源 → 改不了它的 CSS**（浏览器强制）。而用户要的 G4「配色与 Hana 一致」正需要改 CSS。

反代之后：浏览器连的是**我们的服务**，跨源消失，HTML 由我们改写。而且请求从我们的服务出去是**本地回环**，magpie 对回环免 key，`SameSite` cookie 的坑一并绕过。

### 目录布局

```
{HANA_HOME}/apps/magpie-hana/            ← 插件包（只读）
  manifest.json
  index.js                                ← App 入口
  vendor/
    magpie-windows-amd64.exe              ← exe 随包走
    LICENSE-magpie                        ← MIT 版权声明（合规义务）
    version.txt                           ← 打包时的版本号
  ui/                                     ← 卡片页面（若有）
  doc/                                    ← 本目录

{HANA_HOME}/app-data/magpie-hana/        ← 运行时（可写、卸载保留）
  bin/
    magpie.exe                            ← 从 vendor/ 播种
    data/                                 ← 便携模式，magpie 的家当
      providers.json
      plugin-auth.json
      plugins/node_modules/
      usage.jsonl
  runtime.json                            ← 端口 / web key / pid / 版本
  logs/
```

### 启动时序（`apply` 里）

```
1. 确保 bin/magpie.exe 存在
     否 → 从 apps/magpie-hana/vendor/ 复制过去
2. 确保 bin/data/ 存在（触发便携模式）
3. 读取 / 生成 MAGPIE_WEB_KEY（16+ 字符，持久化到 runtime.json）
4. 探测 3425：
     有 magpie 在服务 → 记录「外部在服务」，不启动自己的
     没有 → 启动 magpie web
5. 健康探测（3425 + 3430）
6. 启动反代服务，打 readyMarker
7. 注册 magpie 工具
```

## 六、版本播种规则（必须一开始就定死）

**问题**：magpie 会自我更新，把 exe 换成比包里更新的版本。
**冲突**：如果包里那份旧的会覆盖它，就会降级。

**规则**：

| 场景 | 行为 |
|---|---|
| `bin/magpie.exe` **不存在** | ✓ 从 `vendor/` 播种 |
| `bin/magpie.exe` **已存在** | ✗ **绝不自动覆盖**，哪怕包里更新 |
| 用户手动点「还原内置版本」 | ✓ 覆盖（这是显式动作） |

不这么定的话会发生：用户更新到 0.1.9 → 你发了个带 0.1.8 的插件新版 → 一装 → **降级**。

**更新判断方式**：更新前后各跑一次 `magpie --version` 比版本号。
**不解析其它命令的文本输出** —— 那才是会随版本漂的东西。

**更新后必须重启进程**：Windows 上运行中的 exe 不能被覆盖，只能改名让位，所以新版本要重启才生效。

## 七、已知的漂移风险（诚实清单）

「作者更新不用重新适配」这个目标，能到什么程度：

| 依赖项 | 漂移风险 | 失败表现 |
|---|---|---|
| `--version` / `healthcheck` 退出码 | 极低 | — |
| `/v1/models`、`/v1/magpie/quotas` | 低（正式契约） | 工具报错 |
| `magpie web` 的启动方式与 `MAGPIE_WEB_KEY` | 低 | 起不来 |
| CLI 子命令名（`provider` / `agents` …） | 中 | 对应动作失效 |
| **DOM 选择器**（`data-ptab` / `#view-*`） | **中** | **藏的功能重新冒出来**（不会白屏） |
| CSS 变量名（`--bg` `--accent` …） | 中 | 主题注入失效，退化成原配色 |

**应对原则：按能力探测，不按版本分支。**
启动时探一遍「这个端点通不通、这个子命令在不在」，得到能力集，缺什么就降级隐藏什么。
版本号**只用来显示**，绝不写 `if version >= x`。

## 八、待验证的假设（编码前应先跑）

| # | 假设 | 验证方式 | 风险 |
|---|---|---|---|
| A1 | 宿主 `service` 挂载能同源挂上我们自己的服务 | 写个假的几十行服务先验 | 低（不碰 magpie） |
| A2 | 反代改 HTML 后，注入的 CSS/JS 能生效 | 同上 | 低 |
| A3 | `app-data` 下的 exe 能被沙箱正常执行 | 隔离环境实测 | 中 |
| A4 | 便携模式迁移后，那三个订阅登录仍有效 | 复制 `~/.config/magpie` 到 `data/`（**复制不是移动**） | **高** |
| A5 | 前端 CSS 变量覆盖到「看起来像 Hana」的程度 | 视觉判断（用户拍板） | 低 |

> **A4 是唯一有真实代价的**。用户当前对话模型走的是 WorkBuddy，它的登录存在 `plugin-auth.json`。
> 若迁移后失效，需要重新登录 WorkBuddy —— 在那之前该模型不可用。
> 所以：**先验证功能（隔离环境、不迁配置），确认链路通了，再迁配置**。迁移用「复制」，原文件保留可回退。

| 决策 | 结论 |

## 十三、当前实现结构

```
manifest.json          卡片声明 service: {id: "magpie-ui", path: "/"}；minAppVersion 0.1023.0
index.js               exe 播种 / 托管 runtime / 主题映射 / magpie 工具 / 路由
runtime/proxy.mjs      反代 + spawn magpie web + base 垫片 + 主题与隐藏注入（含 /_hana/* 内部端点）
ui/settings.html       设置页（状态、起停、功能隐藏开关）
assets/icon.svg        App 身份图标
assets/cover.svg       卡片封面（同时放在 ui/assets/ 供 face.image 用）
vendor/                内置 magpie exe + MIT 许可证 + 版本号
doc/                   本目录
tools/selftest.mjs     隔离自测脚本
```

**关键设计修正（相对最初设想）**：不再用「卡片 iframe 直连代理端口」，改用官方的
`contributes.cards[].service` 受管服务挂载 —— 宿主把服务挂在自己的 origin 下，
同源，没有跨源与 CSP 负担。代价是 magpie 的绝对路径 API 调用需要 base 垫片补齐前缀
（已在 proxy.mjs 的 `BASE_SHIM` 里实现）。

## 十四、给接手者的最后提醒

1. **先读第四节的红线。** 用户的对话真的会断。
2. 永远用隔离环境测试（临时目录 + 便携 data + 假 HANA_HOME + 随机端口）。
3. 只依赖第二节「对外接口」表格里的前三层，绝不碰私有配置文件。
4. 参考 `comfyui-hana` 的骨架 —— 同型 App，起停、工作区、主题注入都有现成做法可抄。
5. 有不确定的，**验证事实，不要推断**。这份文档里的事实都标注了来源；推测的部分明确写了「待验证」。
