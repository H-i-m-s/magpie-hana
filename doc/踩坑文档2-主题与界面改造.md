# Magpie-Hana 踩坑文档 · 第二轮（主题与界面改造）

上一份 `踩坑文档.md` 记的是「从骨架到跑通」那一天的 8 个坑。
这一份接着记 **v0.3.0 → v0.4.x** 这一轮：把界面调顺、把主题做对。

两轮的性质很不一样，这点值得先说清：

- 第一轮的坑，几乎全是**和外部边界有关**（宿主转发、上游头、magpie 的 DOM）。
  我在自己这侧跑得好好的，一到真实消费侧就坏。
- 这一轮又分三拨：一半是**我自己制造的第二手错误**（改 A 忘 B），
  一半是**判断错了**（把劫持当适配），还有几个是**验证路径和真实路径不一致**、
  **找错了源文件**（用户提另一个需求时顺带爆出来的）。

所以这份文档里，除了「根因 + 修法」，我还专门标出几个**模式**。
单个坑可以防，模式才值得记。

时间跨度：2026-10-04 到晚，v0.3.0 到 v0.4.x。

---

## 一句话教训

**「适配」和「劫持」之间，只隔着一个 `!important`。**

我为了让卡片配色跟 Hana 一致，用 `!important` 压住了 magpie 的全部颜色变量，
还往它自己的 `data-theme` 属性上写值。从我的角度看，界面终于统一了，
这叫适配。从 magpie 的角度看，**它的设置项被焊死了**：用户点「浅色」没反应，
点完 15 秒我又把属性改回去。

而更要命的是：**我甚至没意识到自己做了什么**。直到用户说
「深浅色切换不了」，我才回头看到那段代码。

> **改别人的界面时，问一句：我是在给它上色，还是在替它做决定？**

## 坑 9：用 `!important` 压住 magpie 的全部颜色变量，把它的「外观」开关焊死了

### 现象

用户在 magpie 自己的设置页里点「外观：浅色 / 深色」，**完全没反应**。
而且卡片配色和 Hana 主题有时候对不上。

（这个坑是用户报出来的，不是我测出来的。这点值得记：我给配色写了那么多
验证脚本，没有一条会去点 magpie 自己的开关。）

### 根因

v0.3.x 的主题注入是这么写的：

```js
// 我注入的样式
html:root{ --bg: #3B4A54 !important; --card: #445560 !important; ... }

// magpie 自己的主题规则
:root[data-theme="light"] { --bg: #f4f4f6; ... }
:root[data-theme="dark"]  { --bg: #1a1a1e; ... }
```

`!important` 一压，magpie 的两套明暗规则**全部失效**。用户在设置页点浅色，
magpie 老老实实把 `data-theme="light"` 写上去了，但颜色早被我锁死，
页面上一点变化都没有。

更隐蔽的是第二刀：**我注入的脚本还会往 `data-theme` 属性上写字**。
用户点完浅色，属性是 `light`；我 15 秒一轮的定时器跑到，又把它算成 `dark`
写回去。于是那个开关点了等于没点。

### 修法

**分开「谁决定明暗」和「谁提供颜色」。**

- 不再写 `data-theme`，改成**只读**它。那是 magpie 自己的地盘。
- 颜色仍来自 Hana（这是用户要的），但改成一读一映射：
  - magpie 说「跟随系统」→ 用 Hana 当前主题
  - magpie 说「浅色」→ 用 Hana 的浅色主题（暖纸）
  - magpie 说「深色」→ 用 Hana 的深色主题（青夜）
- 把 magpie 的开关定义成一次**「手动覆盖」**：点它，当场按你的明暗偏好走；
  等你下次在 Hana 里换主题，跟随重新接管。

最后这条是解决「两个诉求打架」的关键。用户既要「跟随 Hana」又要
「magpie 开关能用」，如果只实现其中一个，另一个必然是坏的。
「覆盖 + 下次跟随拿回控制权」让两者共存。

### 教训

**改别人的界面时，分清哪些是你提供的（颜色），哪些是它自己维护的状态（主题属性）。
只碰前者。**

如果一个改动让原作者的某个功能失效了，那不叫适配，叫劫持。
判据很简单：**它的设置项还能用吗？**

## 坑 10：取主题时用不带参数的 `theme.css`，拿到的是默认主题

**这个坑让「跟随 Hana」从第一版起就没对过。整整一轮。**

### 现象

卡片里显示的配色，和用户在 Hana 里实际用的主题**不是同一套**。
用户用的是青夜（深色），卡片里却是暖纸（浅色）。

### 根因

我取宿主主题变量的代码是这样：

```js
const themeName = name || readHanaTheme();      // readHanaTheme() 可能返回 ""
const q = themeName ? `?theme=${...}` : "";     // 取不到就不带参数
```

而**不带参数的 `/api/apps/theme.css` 返回的是 Hana 的「默认主题」（暖纸）**，
不是用户当前主题。实测：

```
GET /api/apps/theme.css                -> --bg: #F8F4ED   ← 暖纸（默认主题）
GET /api/apps/theme.css?theme=midnight -> --bg: #3B4A54   ← 青夜（用户实际主题）
```

所以只要 `readHanaTheme()` 某个环节返回空，我就安静地拿到暖纸，
而且**看起来完全正常**：200、有 CSS、有变量。没有一行错误。

### 修法

**永远不省 `?theme=` 参数。** 拿不到主题名时，自己按 Hana 的规则解析：

```js
let themeName = String(name || "").trim();
if (!themeName) {
  const raw = readHanaTheme();
  themeName = raw && raw !== "auto" ? raw : HANA_AUTO_DARK;   // 兜底用青夜
}
```

### 顺带发现的第二个问题

`readHanaTheme()` 读到 `"auto"` 时会返回空（早先写了 `t !== "auto"`）。
但 Hana 的 `auto` 其实会解析成一个具体主题。也就是说，**用户只要用了
「自动」，我这边就必然拿到默认主题**。

### 教训

**一个「取不到就退回默认」的分支，如果退回的默认值看起来是合法的，
它就会安静地错下去。**

这类分支要特别当心：它不会报错，不会崩，只是给你一份**错的但看起来对**
的数据。写的时候问一句：这个兜底值，和真实值能不能区分开？
如果不能，那就不是兜底，是伪装。

## 坑 11：内部端点少一个 `.catch()`，整个代理进程猝死

**这条差点让我在错误的方向上找一整天。**

### 现象

我写了个验证脚本，连续打代理的几个 `/_hana/*` 端点。
结果：**第一个请求正常返回，第二个请求直接 `ECONNRESET`，代理进程没了。**

奇怪的是，`status` 端点怎么打都没事，换成 `theme?theme=...` 就打挂。

### 根因

代理内部的端点调度是这样：

```js
handleInternal(req, res).then((handled) => {
  if (!handled) sendJson(res, { ok: false, error: "unknown internal endpoint" }, 404);
});
// ↑ 没有 .catch()
```

`handleInternal` 是个 async 函数，里面会 `await fetchThemeCss(...)`。
而 `fetchThemeCss` 里用的是 `httpRequest`，**它可能在同步阶段就抛异常**
（端口、参数不合法等）。

同步抛出的异常在 async 函数里变成一个 **rejected promise**。
没有 `.catch()` 接住，就是未处理的 rejection。

**Node 15+ 对未处理的 rejection，默认行为是让进程直接退出（退出码 1）。**

于是：某个端点内部一抛异常，整个代理进程死。而对外表现，
只是「这个请求断了」，别的什么线索都没有。

### 修法

```js
handleInternal(req, res).then((handled) => {
  if (!handled) sendJson(res, { ok: false, error: "unknown internal endpoint" }, 404);
}).catch((e) => {
  state.lastError = "内部端点异常：" + e.message;
  log(state.lastError);
  try { if (!res.headersSent) sendJson(res, { ok: false, error: state.lastError }, 500); else res.end(); } catch {}
});
```

再加进程级兜底，宁可留日志也别静默死：

```js
process.on("unhandledRejection", (e) => { state.lastError = "unhandledRejection：" + e.message; log(state.lastError); });
process.on("uncaughtException",  (e) => { state.lastError = "uncaughtException："  + e.message; log(state.lastError); });
```

同时把 `fetchThemeCss` 里可能同步抛的 `httpRequest` 包进 `try/catch`，
让它老老实实 `resolve({ ok: false, error })`，而不是把异常往上抛。

### 教训

**`promise.then(...)` 而不接 `.catch()`，等于埋了一颗进程级的雷。**

而且它**挑路径引爆**：不碰异常路径的端点永远正常，碰到的就当场崩。
所以症状会伪装成「某个功能坏了」，而不是「代码有 bug」。

写任何返回 promise 的调度器时，`.catch()` 不是可选项。

## 坑 12：缝补式改注入脚本，改 A 忘 B，一串连带错误

**这不是一个坑，是一类。而且这一轮里它占了所有 bug 的三分之一。**

### 现象

改完主题逻辑后，卡片里**完全没有注入样式**：`--bg` 一直是 magpie 的默认值。
但诡异的是，**控制台什么都不报**，日志里也一片安静。

### 根因（三个错叠在一起）

我用「按行号 splice」的方式改那个内嵌在 `proxy.mjs` 里的客户端脚本。
快是快，但每次只看得见我要替换的那几行，看不见全局。于是：

**① 误删了一个函数定义。**

替换 `wantedName()` 时，我顺手把上面连着的一段注释一起吃了。
而 `schemeOf()` 恰好夹在注释和 `wantedName()` 之间，**被一起删掉了**。
调用处还在：

```js
if (... && schemeOf(v) && schemeOf(v) !== dt) { ... }
//         ^^^^^^^^^ 未定义
```

`render()` 跑到这里抛 `ReferenceError`，被链尾的 `.catch(function(){})` 吞掉。
于是样式永远注入不进去，而且**一声不吭**。

`node --check` 只做语法检查，**识别不出「引用了不存在的函数」**。

**② 同一个函数名下留了两份。**

`render()` 被改过一次，新版写在了前面，旧版没删干净，**两份并存**。
JS 里后定义的同名函数会覆盖前一个，于是实际执行的是**旧的那份**。
我盯着看的、以为在跑的那份，根本没生效。

**③ 改名之后，残留引用没清。**

把 `appliedName` 改成 `appliedKey` 时，有几处引用漏改。同样是静默失败。

### 修法

**整段重写，不要在运行的代码上缝补。**

这次最终是把整个客户端脚本函数区按旧版行号区间整体替换，
再逐个 grep 检查旧标识符有没有残留：

```powershell
Select-String -Path $f -Pattern "appliedName|wantedName|schemeOf|function render"
```

同类函数名出现两次以上，就是没删干净。

### 教训

> **在一个内嵌的大字符串里按行号缝补代码，等于在通着电的电路上改线。**

三条具体纪律：

1. **改这种内嵌脚本，整段重写，不要按行替换。** 缝补的收益是省几行，
   代价是失去全局视野。
2. **`node --check` 通过 ≠ 代码正确。** 它只查语法。引用错、重复定义、
   残留旧名，它一个都不管。
3. **`.catch(function(){})` 会把错误也一起吞掉。** 静默兜底很有诱惑力
   （"至少不会崩"），但代价是失败变得不可见。至少该往 `state.lastError`
   或控制台写一笔。

## 坑 13：`sendJson` 隐式返回 `undefined`，被当成「未处理」又补一次 404

### 现象

`/_hana/status` 返回的 JSON 里带一条：

```
err=内部端点异常：Cannot write headers after they are sent to the client
```

但 HTTP 状态码还是 200，响应体也正常。

### 根因

内部端点的约定是：**返回 `true` 表示「我处理了」**。

```js
handleInternal(req, res).then((handled) => {
  if (!handled) sendJson(res, { ok: false, error: "unknown internal endpoint" }, 404);
});
```

而路由里是这么写的：

```js
if (path === "/_hana/status") {
  sendJson(res, { ok: true, ... });   // 没有 return
  return true;
}
```

不。真正的问题是那些**写成 `return sendJson(...)`** 的地方：

```js
if (path === "/_hana/theme" && req.method === "GET") {
  ...
  return sendJson(res, { ok: true, theme: r.theme, vars });   // ← 返回的是 sendJson 的返回值
}
```

`sendJson` 内部只有 `res.writeHead(...)` 和 `res.end(...)`，
**没有 return 语句，所以返回 `undefined`**。

`undefined` 是 falsy，上层就判定「未处理」，于是又走了一次
`sendJson(res, 404)`。但响应头和 body 已经发出去了，第二次写就抛
`Cannot write headers after they are sent`。

### 修法

让 `sendJson` 显式返回 `true`：

```js
function sendJson(res, obj, status = 200) {
  const buf = Buffer.from(JSON.stringify(obj), "utf8");
  res.writeHead(status, { "Content-Type": "application/json; charset=utf-8", "Content-Length": String(buf.length) });
  res.end(buf);
  return true;   // 内部端点用 `return sendJson(...)` 表示「已处理」
}
```

### 教训

**用一个函数的返回值当控制信号，就要确保它真的返回那个值。**

`return someFn()` 这种写法很自然，但 `someFn` 的返回值是
「碰巧是 undefined」还是「刻意设计的标志」，完全取决于它内部写没写 return。
一个隐式的 `undefined` 就能让控制流走错分支。

## 坑 14：挂载前缀在根路径拼出双斜杠

### 现象

直接访问代理（不经卡片）时，主题跟随的轮询**完全不工作**。
但在卡片里是好的。

### 根因

客户端脚本要先算出「自己挂在哪个路径下」，再往这个前缀上拼端点地址：

```js
function mountBase(){
  var p = location.pathname || "/";
  return (p.length > 1 && p.charAt(p.length - 1) === "/") ? p.slice(0, -1) : p;
}
var BASE = mountBase();
fetch(BASE + "/_hana/host-theme");
```

- 卡片里，`pathname` 形如 `/api/apps/<id>/routes/_runtime/<rid>/_surface/<token>/`
  → 剥掉末尾斜杠 → 拼出正确的路径。
- 直接访问代理时，`pathname` 就是 `/`。`p.length > 1` 不成立，
  **原样返回 `/`** → 拼出 `//_hana/host-theme`。

双斜杠路径代理不认，请求被当成普通转发打给了 magpie，于是轮询永远失败。

### 修法

根路径明确返回**空串**：

```js
function mountBase(){
  var p = location.pathname || "/";
  if (p === "/") return "";
  return (p.charAt(p.length - 1) === "/") ? p.slice(0, -1) : p;
}
```

### 教训

**「剥掉末尾斜杠」这类路径处理，边界值就是那个「只有斜杠」的路径。**

`p.length > 1` 这个条件看起来是在防「空字符串」，实际上顺手放过了
唯一真正危险的输入 `/`。写路径处理时，把边界值一个个列出来试：
`""`、`"/"`、`"/a"`、`"/a/"`。这个坑在第四个输入上。

## 坑 15：把「一张变量表」当成了「主题名到变量表的映射」

### 现象

客户端按主题名取变量时，**命中了一份牛头不对马嘴的表**。
具体表现是颜色不跟随，且切换主题后取到的仍是最初那套。

### 根因

服务端注入页面时，会给两份东西：

```js
window.__hanaThemeChoice = "auto";       // 当前选择
window.__hanaVars = { "--bg": "...", "--text": "...", ... };   // 一张变量表
```

而客户端有个缓存，本来是「主题名 -> 变量表」：

```js
var cache = {};
// 错误的初始化：把 __hanaVars 的每个变量名当成了主题名
for (var k in window.__hanaVars) cache[k] = window.__hanaVars[k];
```

`__hanaVars` 的 key 是 `--bg`、`--text` 这种变量名，
而 `cache` 期望的 key 是 `midnight`、`coral` 这种主题名。
于是 `cache["--bg"] = "#3B4A54"` 这种条目被塞进去了，
而 `cache["midnight"]` 压根不存在。

### 修法

**种子变量表单独放，不要往按名索引的缓存里塞。**

```js
var cache = {};
var seedVars = (window.__hanaVars && typeof window.__hanaVars === "object") ? window.__hanaVars : null;
```

`seedVars` 只在一处用：请求的正好是宿主当前主题、而还没取到时，当首屏兜底。

### 教训

**两个都是对象、都能 `for...in`，不代表它们的语义可以互换。**

`{ "--bg": "#3B4A54" }` 和 `{ "midnight": {...} }` 在 JS 里长得一样，
但在语义上一个是「一条记录的字段」，一个是「索引」。
把它们混起来，代码不会报错，只会安静地错。

命名上就该区分开：`cache`（按名索引）和 `seed`（一份快照）。
如果两个变量名字看不出区别，那离搞混就不远了。

## 坑 16：`data-theme` 分支短路了轮询值，让「实时跟随」形同虚设

### 现象

轮询明明拿到了新主题名（`hostName` 已经从 `midnight` 变成 `coral`），
页面却**一点都不动**。

### 根因

主题选择的判定函数里，分支顺序错了：

```js
function wantedName(){
  var choice = window.__hanaThemeChoice || "auto";
  if (choice !== "auto") return choice;
  var dt = document.documentElement.getAttribute("data-theme") || "";
  if (dt === "light") return P.light || "warm-paper";
  if (dt === "dark")  return P.dark  || "midnight";
  return hostName || P.theme || "";   // ← 轮询值排在这三个分支后面
}
```

而 magpie 自己的设置里 `theme` 是 `"dark"`，所以 `data-theme="dark"` 一直挂着。
**`dt === "dark"` 这条永远先命中**，`hostName` 根本轮不到。

诊断出口读出来的状态把这个矛盾摊得很清楚：

```
hostName:  "coral"       ← 轮询拿到了，是新的
appliedKey: "midnight|"  ← 但实际应用的一直是旧的
```

### 修法

把语义重新分层，而不是调分支顺序：

- `hostName`（轮询值，代表"Hana 当前是什么"）**最优先**。
- `data-theme`（magpie 的明暗偏好）**只在明暗冲突时才插手**：
  用户在 magpie 里要深色，而 Hana 正用浅色主题，那就切到 Hana 的深色主题；
  明暗一致时不插手，好让 Hana 的具体色调活着。

关键是从「谁的名字排在前面」改成「谁在什么条件下说话」。

### 教训

**一串 `if` 按顺序返回，等于给这些条件排了优先级，而这个优先级
往往不是有意设计的，只是写的顺序。**

写这种多来源的取值函数时，别问「先写哪个」，
要问「这几个来源，各自的权威范围是什么」。
如果答案是「A 只看明暗，B 管具体主题」，那就不该是线性分支，
应该是分层的判断。

## 坑 17：设置页用裸 `fetch` 打路由，所有写操作都是 403（而且是静默的）

**这个坑存在了一整轮都没被发现。因为它的表现太像「能用」了。**

### 现象

用户报了一个看似无关的诉求：「我更希望用类似 git-save-load 那种下拉菜单的形式」。

我在改造设置页的过程中顺手测了一下保存，发现它返回 `forbidden`。
回头查，**设置页从第一版起就写不进任何东西**：无论是切换主题还是开关隐藏功能。

### 根因

设置页跑在宿主的沙箱 iframe 里，它给后端路由发请求时**必须带凭据**。
而宿主的凭据是在 iframe URL 里以 `appSurfaceSession` 下发的，
由 SDK 转成一个请求头：

```js
// sdk/ui.js 里 pluginApiFetch 的实现（简化）
const session = readSurfaceSession(window);          // 从 URL 取 appSurfaceSession
headers.set("X-Hana-App-Surface-Session", session);  // 转成请求头
return fetch(pluginApiUrl(...), { headers });
```

我那一版设置页用的是**裸 `fetch`**，它带不上这个头。
路由端（`connectionKind: "local"`）判定无凭据，一律 403。

实测四种写法，全部 403：

```
裸 fetch                         -> 403 missing_credential
credentials: 'include'           -> 403 missing_credential
XMLHttpRequest                   -> 403 missing_credential
带 Cookie                        -> 403 missing_credential
```

而同项目里别人的设置页（git-save-load / doc-intake / llama-monitor）
**无一例外**都走 `hana.api.fetch`。我当初抄的是结构，没抄这一行。

### 为什么一直没被发现

三个因素叠在一起：

1. **失败是静默的。** 页面没有报错弹窗，`fetch` 拿到 403 只是个普通响应，
    `.json()` 照样能解析出 `{error: "forbidden"}`。界面看着完全正常。
2. **我自己验证时走了另一条路。** 我用 node 直接打路由（带 query token），
   那是**能通**的；于是我以为「保存功能是好的」。验证路径和真实消费路径
   不一致，这正是上一份文档结尾说的那类错。
3. **App 数据里的确存着值。** `ui.json` 里有 `hidden`、`theme`，
   看起来像是保存过。**那是我用 node 测试写进去的**，不是设置页写的。
   一个「看起来有数据」的文件，反而成了误判的帮凶。

### 修法

改用 SDK 的 `hana.api.fetch`，路径传**相对**形式：

```js
import { hana } from './assets/sdk.js';

const ROUTE = '/magpie-hana';

async function api(path, init) {
  const r = await hana.api.fetch(path, init);   // SDK 拼前缀 + 注入凭据头
  return r.json();
}

await api(`${ROUTE}/status`);
```

**两个必须注意的点**（我都踩了）：

- **路径必须是相对的。** SDK 的 `normalizePluginApiPath` 明确拒绝
  `api/apps/...` 开头的绝对路径（会直接抛「Invalid plugin API path」）。
  我只传 `/magpie-hana/status` 这样的相对段，由 SDK 拼成
  `/api/apps/magpie-hana/routes/magpie-hana/status`。
- **要先 `await hana.ready()` 再发第一个请求。** 兄弟 App 的 boot 顺序都是
  `await hana.ready()` → `refresh()`。

### 教训

**验证路径必须和真实消费路径一致。**

我用 node 测「接口能不能写」，接口确实能写；但用户操作时走的是
「设置页 iframe 里的 fetch」，那是另一条路。这两条路只差一个凭据头，
结果一个通一个 403。

还有一层：**当失败表现为「一个看着正常的响应」而不是「一个错误」时，
它就能躲过所有不专门找它的验证。** 这和坑 12、13、15 是同一个模式。

## 坑 18：原生 `<select>` 的弹出面板跟不了主题

### 现象

设置页的主题选择器是个原生 `<select>`。它在深色卡片里展开时，
弹出的是一个**由系统绘制**的选项面板 —— 亮底色、系统字体，
和整个深色调的卡片格格不入。

用户的原话是「我更希望使用类似 git-save-load 这种下拉菜单的形式」。

### 根因

原生 `<select>` 的**触发器**可以用 CSS 改样式，但**展开后的选项面板
由操作系统/浏览器绘制**，不受页面 CSS 控制，也不跟随主题变量。
所以它注定是所有控件里最突兀的一个。

### 修法

抄 git-save-load 的自绘下拉（`HanaSelect`），思路是：

> **原生 `<select>` 留着当状态源（藏起来），上面盖一套自己的
> 触发器 + 悬浮面板，视觉与交互全部自己画。**

关键实现点：

- 面板挂到 `document.body` 上（不是触发器内部），用 `position: fixed` 定位。
  这样它不会被祖先元素的 `overflow: hidden` 裁掉。
- 定位时量触发器矩形，贴在它下方 4px；下方空间不够就翻到上面；
  再不够就限制高度 + 内部滚动。
- 颜色全部用宿主主题变量（`--bg-card` / `--border` / `--text` / `--accent`），
  这样它天然跟随主题。
- **页面滚动/尺寸变化时直接关掉面板。** fixed 定位的面板不会跟着触发器走，
  留着就会飘在原地。关闭是最省事也最稳的做法。

### 顺便：下拉里该分层的两项

主题选择器里有两种语义：

- `自动（跟随 Hana）` —— 一种**策略**
- `青夜` / `暖纸` / `珊瑚` ... —— 具体**主题**

它们不是同级的东西。我在「自动」和具体主题之间加了一条细分割线，
让「一个开关」和「一组选项」在视觉上分开。

### 教训

**要判断一个控件能不能跟主题，先问：它展开后的那部分是谁画的？**

原生 `<select>`、原生菜单、系统对话框，这些「逃出页面 CSS 管辖」的部分，
是主题一致性的天然破口。要么就不用它们，要么就像这里一样自绘一层。

## 坑 19：换图标时抓错源，又把封面放错目录

**这个坑叠了两层，任何一层单独拿出来都不足以解释「改了却没效果」。**

### 现象

用户说「你卡片图标还没改成 magpie 的应用图标」。
而我上一轮明明已经换过图标了。

### 第一层：抓错了源文件

magpie 仓库里有好几个长相相近的鸟：

| 文件 | 用途 |
|---|---|
| `internal/gui/assets/icons/favicon.svg` | 网页图标：**只有鸟**，黑/白随系统 |
| `internal/gui/assets/icons/magpie.svg` | 头部 logo：同上，去掉了眼睛 |
| `build/icon/magpie.svg` | **应用图标**里的鸟（带眼睛的完整版） |
| `build/windows/icon-*.png` | 真正构建出来的 app 图标 |

我抓的是 `favicon.svg`（只有鸟），然后自己配了**深蓝底 + 白鸟**。
而 magpie 真正的应用图标是 **白底（#FFF→#ECECEC 竖向渐变）+ 墨色鸟（#161616）**，
方向正好反了。而且我用的是**没眼睛**的版（favicon 是 small 系列），
官方 64px 以上用带眼睛的完整版。

所以看起来「没区别」：都是鸟，只是换了个底色，鸟本身几乎一样。

### 第二层：封面放错了目录（更隐蔽）

我改了好几轮的都是 `assets/cover.svg`（app 根下）。
但官方文档写得很清楚（APPS.md）：

> `face.image` 是**相对应用 `ui/` 目录**的路径。

五个兄弟 App 的实际布局佐证了这一点：comfyui-hana 的 `cover.png`
**只在 `ui/assets/` 下**，根 `assets/` 里根本没有。

而顶层 `icon` 是相对 **app 根**的（五个 App 的 `assets/icon.*` 全在根下，
`ui/assets/` 里一个都没有）。两个字段基准不同，我把它们当成同一个了。

所以真相是：

- **顶层 App 图标**：我改对了（在 app 根）
- **卡片封面**：我改的是一直没被引用的那个文件；真正生效的是
  `ui/assets/cover.svg`，里面还躺着最早期的占位图

### 修法

去看 magpie 的**图标生成源码** `build/icon/gen.go`（那就是图纸）：

```go
// macOS icon grid: the squircle occupies ~80% of the canvas
inset := S * 0.1
side := S - 2*inset
radius := side * 0.225
k := side * 0.8 / 44              // 鸟缩放到 44 单位网格的 0.8
o := inset + side/2 - 22*k        // 居中
bg1, bg2 := 0xff, 0xec            // 白 -> #EC
ink := 0x16                       // 鸟用 #161616
```

照着它重写 SVG（用带眼睛的 `build/icon/magpie.svg` 路径），
再把封面**放到它真正该在的地方** `ui/assets/cover.svg`，
删掉根目录那个从没生效过的。

验证：无头 Edge 渲染成 256x256，与官方 `build/windows/icon-256.png`
逐像素比对——

```
有效区域平均 RGB 差异:  1.93 / 765
显著差异像素:          74 / 40516 = 0.18%
关键点（方块中心/顶部/底部）：245/246、252/252、239/239
形状不一致 10%，全在圆角边缘的抗锯齿带
```

### 教训

**「不存在的东西，看起来和不生效差不多。」**

一个未被引用的文件躺在与引用路径仅一字之差的地方，
我每次改它都以为在改封面，实际上什么都没发生。
更坏的是：文件确实存在，`git status` 也显示变更，
所有本地检查都“通过”。

三条具体纪律：

1. **找素材去图纸所在的层，不要在成品堆里随便挑。**
   `build/icon/gen.go` 是图纸，`*.png` 是成品。读图纸能拿到
   精确参数（圆角比例、渐变端点、缩放系数）。
2. **确认字段的路径基准。** 同一份 manifest 里，
   `icon` 相对 app 根、`face.image` 相对 `ui/`，不一样。
   别拿 A 的经验套 B。
3. **改完之后要问“宿主真的会读到这个文件吗”，**
   去取一次（或看看别的 app 怎么放），别只看本地文件变了没。

## 排查方法：我看不见卡片，怎么知道主题有没有生效

这一轮最有用的能力，不是某个修法，而是**一套在「看不见界面」时
仍然能量准状态的方法**。第一轮的坑 8 也是靠它破的。

### 1. 用无头浏览器 + CDP 量渲染后的真实值

不能截图看（截图对我只是一串文件路径），但可以读**计算样式**：

```js
// 无头 Edge 打开代理，用 CDP 求值
getComputedStyle(document.documentElement).getPropertyValue('--bg')
// -> "#3B4A54"
```

这比读源码、读响应体都硬：它量的是**浏览器实际用起来的值**，
CSS 优先级、注入顺序、`!important` 冲突，全都算进去了。

配套的还有：元素坐标 `getBoundingClientRect()`（用来验头部布局），
`document.styleSheets.length`（用来验样式表数量）。

### 2. 在页面里留一个只读的诊断出口

```js
window.__hanaThemeDiag = function(){
  return { choice, hostName, urlTheme, appliedKey, cacheKeys, dataTheme, styleLen };
};
```

这个函数的建立，是这一轮的转折点。在它之前，我只能在外部猜
「脚本里到底发生了什么」；有了它，冲突的两个值（`hostName` 是新的、
`appliedKey` 是旧的）一眼就摆出来了。

**教训：给闭包里的状态开一个只读的观察窗，成本极低，收益极大。**

### 3. 给关键操作装探针，记录执行轨迹

```js
// 包装 fetch，记录每一次 _hana 请求
const of = window.fetch;
window.fetch = function(input, init){
  if (String(input).includes('_hana')) window.__trace.push('fetch ' + input);
  return of.apply(this, arguments);
};
```

这一招直接证明了「轮询在发请求，但 `render()` 没动作」，
把故障范围从「整个跟随链路」缩到了「render 内部」。

### 4. 模拟用户操作，别只测静态状态

「在 Hana 里换主题」这个动作，我是**直接改 `preferences.json`** 模拟的：

```js
const j = JSON.parse(readFileSync(PREF, 'utf8'));
j.appearance.theme = 'coral';
writeFileSync(PREF, JSON.stringify(j, null, 2), 'utf8');
// 等 9 秒，看页面有没有自己跟上
```

然后**一定要还原**。测试完不还原，等于给用户留了个坑。

### 5. `node --check` 只能查语法

这一轮吃过两次亏：`schemeOf` 被误删、两份 `render` 并存，
`node --check` 全部通过。**引用错、重复定义、残留旧名，它一个都不管。**
这类问题要靠 grep 检查标识符，或者靠运行时诊断出口。

## 最后：这一轮的三类坑

**第一类：我制造的第二手错误（坑 12、13、14、15）**

它们的共同特征是：**修 A 的代码，弄坏了 B**。

- 加 `.catch()` 之前，一个缺漏就能让进程崩（坑 11）
- 按行缝补，误删了夹在中间的 `schemeOf`（坑 12）
- `sendJson` 不返回 `true`，调度器走了错的分支（坑 13）
- 路径处理的边界值 `/` 被条件放过了（坑 14）
- 两个都是对象，就被当成同一语义混用（坑 15）

它们的共同点：**不会报错，只会安静地错**。

> **安静的错误比响亮的错误危险得多。**
> 响亮的错误会把你引向现场；安静的错误只会让你在别处瞎找。

**第二类：设计层面的错（坑 9、10、16）**

这三个都不是「手滑」，是**判断错了**。

- 我把「压住对方的颜色」当成了「适配」（坑 9）
- 我接受了一个「取不到就退回默认」的分支，没问那个默认值能不能和真值区分（坑 10）
- 我用一串 `if` 给多个数据源排了优先级，却没想过它们各自的权威范围（坑 16）

> **代码写对，不等于设计想对。**
> 前者靠严谨，后者靠先问一句「我到底在决定什么」。

**第三类：验证路径与消费路径不一致（坑 17、18）**

这两个是用户在提另一个需求时顺带暴出来的。

- 我用 node 直连路由测「保存能不能写」，得到能写；但用户操作时走的是
  「设置页 iframe 里的 fetch」，那是另一条路，差了整整一个凭据头（坑 17）
- 原生 `<select>` 的**触发器**能改样式，但**展开面板**由系统绘制，
  不受页面 CSS 管辖 —— 我以为我在调一个控件，其实只调了它的一半（坑 18）

> **「我验过了」要问一句：我验的是哪条路？和用户走的是同一条吗？**
> 验证环境与真实环境差一个字节，结论就可能是反的。

**第四类：找错了对象（坑 19）**

- 用户说「图标还没改成 magpie 的应用图标」，我说「改了」——
  两边都没错：我改的是一个长得像但不对的那个文件（坑 19）

> **做甲事时先确认甲是什么。** 
> 「换图标」这个词里，藏着「哪一个是应用图标」这个问题。
> 跳过它就等于凭空多一次返工。

这一轮我改的是界面和主题，看着比第一轮「轻」。
但坑 9 和坑 17 这两类错误，都具备一个很坏的性质：
**它们不会主动暴露自己，会在那里静静等着。**

坑 9 如果不被用户点出来，它会在**每一次有人想用 magpie 自己的设置时**重复发作；
坑 17 如果不被这个「换下拉」的需求顺带撞到，它会让**设置页永久写不进去** ——
而表面上一切正常。

3. **动手前，先弄清楚「要改的那个东西」到底是哪一个。**
