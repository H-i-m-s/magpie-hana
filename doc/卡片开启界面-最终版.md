# Hana 卡片「开启界面」参考 · 最终版

> 读者：写 Hana App / 插件的作者。
> 结论是一条**协议**，不是一个优化技巧。照抄第三节那八行，卡片就能秒开。
> 本文所有机制都来自 Hana 1.0.4-beta 的渲染端与服务端产物（文件名与常量都写在下文，方便你自己复核）。

---

## 零、一句话结论

**卡片的 iframe 一直挂在 DOM 里，只是 `opacity: 0`。宿主在等卡片文档自己 postMessage 一句 `{type:"ready"}`。**
等不到，它会一直等到 `eu = 5e3` 毫秒（正好 5.0 秒）才强行把卡片掀开。

所以"打开卡片转圈 5 秒、页面本身却只要 0.2 秒"的唯一原因通常是：**卡片文档从来没喊过那一句**。

```js
// 你的卡片页里，加载完成时喊一声
parent.postMessage({ type: "ready" }, "*");
```

---

## 一、症状长什么样

- 打开卡片转圈约 5 秒，**非常稳定**，每次都一样（5.0 秒这个数字本身就是线索：它是个常量，不是"性能差"）。
- 页面本身早就好了：脚本几十毫秒、首屏几百毫秒，跟那 5 秒完全断层。
- 没有报错，没有新进程，Hana 日志在那 5 秒里是空白。
- 换个卡片形态（`cardForm`）、换成 `route` 型、把内容做轻，都不管用。

一句话：**你在等它，它在等你。**

## 二、机制（读 Hana 产物得到的，附出处）

### 2.1 卡片 iframe 一直在，只是透明

`AppUiSurface-*.js` 里，卡片是这样挂的：

```js
<div className={surface} data-app-ui-surface={slot}>
  {f === "loading" && <div className={overlay} role="status"><div className={spinner}/></div>}
  {f === "error"   && <div className={overlay} role="alert">…重试…</div>}
  <iframe ref={iframeRef} className={iframe} src={iframeSrc}
          sandbox="allow-scripts allow-forms allow-popups allow-same-origin"
          style={{ opacity: f === "ready" ? 1 : 0 }} />
</div>
```

`f` 由"路由解析状态"和"iframe 状态"二者决定。**`loading` 时页面其实可能已经画好了，只是看不见。**

### 2.2 宿主等的是一条 ready 信封

`PlanModeButton-*.js` 里的入站消息校验函数：

```js
function Qc(e) {
  if (!isObject(e)) return null;

  if (e.protocol === void 0) {                 // ① 简单形状（最省事，推荐）
    if (e.type === "ready") return { kind: "ready" };
    if (e.type === "navigate-tab" && …) return { kind: "navigate-tab", tab: … };
    if (e.type === "resize-request" && …) return { kind: "resize", size: … };
    return null;
  }

  const t = validateEnvelope(e);               // ② 协议信封形状
  if (!t.ok) return null;
  if (t.value.type === "hana.ready") return { kind: "ready" };   // {protocol,version,kind:"event",type:"hana.ready"}
  …
}
```

收到之后才是"就绪"：

```js
if (B.kind === "ready") {
  clearTimeout(readyTimer);
  …
  setStatus("ready");          // ← 遮罩抬起、iframe 不透明
  onReady?.();
}
```

### 2.3 等不到会怎样：5 秒常量

```js
const eu = 5e3;                                        // ← 就是它
readyTimer = setTimeout(() => { setStatus(readyOnTimeout ? "ready" : "error") }, eu);
```

`readyOnTimeout` 两套取值：

| 挂载场景 | readyOnTimeout | 超时后的表现 |
|---|---|---|
| 卡片表面 `AppUiSurface` | `false` | 变 `error`（显示"加载失败 + 重试"） |
| 桌面/预览 `CardShell` 等 | `true` | **变 `ready`**（什么也不说，硬掀开） |

这解释了为什么"转圈几秒后还是打开了"，而不是报错：**你看到的那次就是超时被强行掀开。**

### 2.4 消息必须来自卡片文档本身

```js
function Yc(e, iframeWin, expectedOrigin) {
  return !iframeWin || !expectedOrigin || e.source !== iframeWin ? false : e.origin === expectedOrigin;
}
```

`expectedOrigin = new URL(iframeSrc).origin`。

⇒ **只有卡片文档自己的窗口、从它自己的源发出的消息才算数。**内层 iframe、代理页面、任何第三方页喊都无效（我们踩过：壳子里嵌的 magpie 页喊了没用，得壳子自己喊）。

### 2.5 别的 App 确实是这么做的（实测旁证）

这不是我们发明的写法，两个现成的 App 都喊了，只是抽象层次不同：

| App | 怎么喊 | 位置 |
|---|---|---|
| `hanako-gallery` | 裸消息 `(window.parent \|\| window).postMessage({ type: "ready" }, "*")` | `ui/panel.html` 的 `<head>` 里，紧跟样式，注释里还写着"撑满一个写死的 5 秒超时" |
| `token-tracker-app` | 自带一份官方 UI SDK（`ui/sdk/ui.js`，104KB，`plugin-protocol` 构建），走协议信封：`postReady()` → `postEvent("hana.ready", …)` | `ui/bootstrap.mjs` 调 `hana.ready()` |

两种合法写法，`Qc()` 都收：

```js
// 甲：裸消息（最省事，图库这么写）
parent.postMessage({ type: "ready" }, "*");

// 乙：协议信封（官方 SDK 的 hana.ready() 内部就是这条）
parent.postMessage({
  protocol: "hana.plugin.ui", version: 1, kind: "event",
  type: "hana.ready", payload: {}
}, "*");
```

两点提醒：

- 写在哪：**样式之后**（CSS 已加载，不会闪一屏未样式化内容），但**在做重活之前**。
- 那条超时常量在不同版本的产物里**压缩名不一样**（1.0.4-beta 里是 `eu`，图库那份注释里记的是 `Es`），但**值都是 `5e3`**；认值，别认名字。

## 三、最小可用卡片页（照抄）

```html
<!doctype html>
<html lang="zh">
<head>
<meta charset="utf-8">
<title>我的卡片</title>
<style>html,body{margin:0;height:100%;background:var(--bg,var(--hana-bg,transparent));color:var(--text,var(--hana-text,#6b7681))}</style>
</head>
<body>
<div id="app">正在启动…</div>
<script>
(function () {
  // ① 先报到：宿主等的就是这一句。缺了它，无论页面多快都要等到 5 秒超时。
  function sayReady() {
    try { parent.postMessage({ type: "ready" }, "*"); } catch (_) {}
  }
  sayReady();
  // 补喊几次：宿主可能比我们晚一步装上监听。重复喊是无害的。
  [60, 300, 1000].forEach(function (d) { setTimeout(sayReady, d); });

  // ② 再干活：画界面、取数、内嵌，都放在这里。
  document.getElementById("app").textContent = "已就绪";

  // ③ 需要的话，顺便告诉宿主尺寸或切页（Qc 认识这两个）
  // parent.postMessage({ type: "resize-request", payload: { width: 720, height: 480 } }, "*");
  // parent.postMessage({ type: "navigate-tab", payload: { tab: "detail" } }, "*");
})();
</script>
</body>
</html>
```

要点：

1. **先喊 ready，再干重活。** 喊完遮罩立刻抬起，用户看到的是你自己写的"正在启动…"，而不是 5 秒转圈。
2. **在卡片文档里喊，不要在它内嵌的页面里喊。**（见 2.4）
3. 只想最省事就用 `{type:"ready"}`；要跟 Hana 的协议信封对齐就用
   `{protocol, version, kind:"event", type:"hana.ready"}`，两种都被接受。

## 四、卡片类型：`route` 还是 `service`

| | `route` 型 | `service` 型 |
|---|---|---|
| manifest | `"route": "/panel.html"` | `"service": { "id": "…", "path": "/" }` |
| 文档由谁伺服 | Hana 的 app-host（`ui/<route>`） | 你自己的服务（经 Hana 的 surface 路由） |
| 需要服务生命周期 | 不需要 | 需要（服务文档 `pending` 时 surface 路由 409） |

**重要更正：那 5 秒和 route/service 无关。**我们一开始把慢归因给 service 型，改成 route 型之后那 5 秒一分不少——真正的原因始终是"文档没喊 ready"。选哪种只看你的界面由谁伺服。

顺带记两条 service 型的坑（本次没用到，读代码所得）：

- 服务文档状态机：`unregistered | pending | ready | stopping | unavailable`，观察是 NDJSON 流（`/api/app-service-status/events`，**host-only**，未授权返回 `Only a host owner may observe service status`）。
- 挂载时若服务状态中途变化，会报 `APP_SURFACE_STALE`。

## 五、CSP：要内嵌本地端口、要 fetch 自己时再声明

不声明 `ui.csp` 时用默认策略：

```
default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';
img-src 'self' data:; media-src 'self' data:; connect-src 'none';
```

声明之后**不是**替换成你写的那串字符串，而是由 Hana 生成一份结构化策略，你只能填四个字段：

| 字段 | 作用 |
|---|---|
| `resourceDomains` | 追加到 `script-src` / `style-src` / `img-src` / `font-src` / `media-src` |
| `connectDomains` | 追加到 `connect-src`（注意：声明了它，`connect-src` 从默认的 `'none'` 变成 `'self'` + 你写的） |
| `frameDomains` | `frame-src`（**要内嵌外部页面才需要**，不填就是 `'none'`） |
| `baseUriDomains` | `base-uri` |

例子（我们要内嵌一个随机端口的本机代理，所以这样写）：

```json
{
  "ui": {
    "csp": {
      "frameDomains": ["http://127.0.0.1", "http://localhost"]
    }
  }
}
```

- 域名**不能带路径或查询**，校验很严；**不带端口 = 匹配任意端口**（所以能对上"每次启动随机挑端口"的本地服务）。
- 协议只接受 `http:` / `https:` / `ws:` / `wss:`。
- 想在卡片里 `fetch` 自己的路由：记得把来源写进 `connectDomains`，否则默认 `connect-src 'none'` 会把它掐掉。

## 六、凭据：卡片文档里怎么调 App 自己的路由

实测：**route 卡片文档里没有注入 `window.hana`**，裸 `fetch` 调自己的路由会静默 403（界面看着正常，数据全是空）。凭据得自己带：

1. **值从卡片 URL 的查询串里取**，参数名 `appSurfaceSession`：

   ```
   http://hana.local/api/apps/<appId>/ui/card.html?appSurfaceSession=<token>&agentId=…&hana-theme=…
   ```

   （同一家族还有：`pluginSurfaceSession`（普通插件）、`appIframeTicket` / `pluginIframeTicket`（票据形态）。）

2. **放请求头回传**，头名 `X-Hana-App-Surface-Session`：

   ```js
   const s = new URLSearchParams(location.search).get("appSurfaceSession");
   fetch("/api/apps/<appId>/routes/<route>/status", {
     credentials: "same-origin",
     headers: s ? { "X-Hana-App-Surface-Session": s } : {}
   });
   ```

3. 会过期，别长期缓存；另外 Hana 的日志会**主动把这两个参数名擦掉**，别指望在日志里找到 token。

## 八、踩坑清单

1. **改了 `route` / `service` 声明，老卡片实例会失效**：报
   `The App directory no longer declares the service this card was opened with.`。
   实例记着"当初是用哪套声明打开的"，`重试`按钮救不了它 —— **删掉这张卡片，重新添加一张**。
2. `ui.csp` 的域名不能带路径/查询，别想写 `http://127.0.0.1:8080/path`。
3. `cardForm`（`flush` / `edge-to-edge`）与 ready 无关，别在这上面找原因。
4. 别在卡片文档里指望 `window.hana`；走第六节那条凭据路。
5. 内嵌页面的 `postMessage` 到宿主是**无效**的（源不对），必须由卡片文档自己代转。
6. **不要自己拍颜色。**平台会往 app 文档里注入主题变量（其它卡片 CSS 就直接写
   `var(--text, …)`、`var(--text-secondary, var(--text-muted, …))`），所以背景/文字这么写：

   ```css
   html, body { background: var(--bg, var(--hana-bg, transparent)); color: var(--text, var(--hana-text, #6b7681)); }
   ```

   **没有变量时保持透明**，让卡片自己的底色透出来。写死一个深色（比如 `#0b0f14`）
   在浅色主题下就会在打开瞬间闪一下黑，而且开发时常常看不见，因为你自己用的是深色主题。
   另外若宿主注入了 `window.__hanaVars`（一张变量表），可以把它套到 `documentElement` 上。

## 九、我们这份样例的实测数字

| 阶段 | 之前 | 之后 |
|---|---|---|
| 卡片遮罩抬起 | 固定 5.0 秒（`eu = 5e3` 超时） | 立即 |
| 卡片文档脚本起步 → 首个请求 | +36 / +45 ms（两次实测） | 同 |
| 内层页面 `boot` → 完全就绪 | ≈ 330 ms | 同 |
| 用户主观 | "每次都要等个几秒" | "直接秒开了" |

排查中**排除掉**的方向（都带量法，避免重走）：代理层开销（1–10ms）、页面资源（3.1MB / ~100ms）、JS 编译（27ms）、每次开卡片新建 webview 进程（没有）、打开卡片导致 app 重载（没有）、文件锁 / Defender / 同步盘（0.59ms/400 次读）、CSP 拦截（默认策略与声明后的策略都允许同源脚本，挡不住东西）。

另外一条**无关但值得知道**的背景：本机 Hana 的会话列表操作存在慢性负载（某天 `sessions_list_timing` 335 次、中位 2097ms、最长 45293ms、累计 973 秒 / 1269 个会话）。它不影响卡片就绪，但会让"点什么都偏慢"。

## 十、出处（便于复核，版本会变，协议相对稳定）

| 事实 | 出处 |
|---|---|
| iframe `opacity` + `sandbox` | `AppUiSurface-*.js` |
| `Qc()` 入站信封校验（`{type:"ready"}` / `hana.ready` / `navigate-tab` / `resize-request`） | `PlanModeButton-*.js` |
| `Yc()` 源与窗口校验 | 同上 |
| `const eu = 5e3`、`readyOnTimeout` 两套取值 | 同上 |
| 卡片 URL 组装（`appSurfaceSession` / `appIframeTicket` / `hana-asset-base`） | 同上（`vc()`） |
| `appSurfaceSession` 与 `X-Hana-App-Surface-Session` 的常量定义 | server 产物（`TD` / `J$`） |
| CSP 生成（`h7r()`）与默认策略（`l7r`）、域名校验（`d7r()`） | server 产物 |

Hana 版本：**1.0.4-beta**（产物名带 hash，会随更新变化；协议字段名和那两个常量才是你要记的）。

## 附：本次完整的排查心路（可跳过）

这份参考里的每一条，都是用同一套办法问出来的：**先证伪自己这一层，再把"对方在等什么"当成一个可以读出来的事实，而不是一句"平台慢"**。

1. 页面侧全量计时 → 我们只有 0.4 秒（排除了自己）。
2. 反复确认"几秒发生在卡片文档被创建之前" → 说明等待发生在宿主侧。
3. 读宿主的卡片挂载路径 → 找到 `opacity: 0` + ready 信封这条协议。
4. 找到常量 `eu = 5e3` → 与"每次稳定 5 秒"精确对上，机制闭环。
5. 补上那一句 `{type:"ready"}` → 秒开。

教训同样重要：**把"我这条链路快"当成"卡片快"**，会让人在错误的层里反复拧螺丝；**把平台的沉默当成"慢"，而不是当成"缺一步协议"**，会让人一直在优化一个逻辑上不可能变快的路径。
