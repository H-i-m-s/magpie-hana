# 卡片打开慢 · 排查记录（2026-10-08）

这一轮排查的对象不是功能坏了，而是**体感**：卡片每次打开都要转圈几秒。
结论提前说：**这个 App 这一侧已经封顶（0.4 秒），剩下的时间在 Hana 盖在卡片上的骨架层。**
下面留的是怎么一层层量出来、排除了什么、以及怎么重跑。

---

## 一、症状与口径（先对齐，不然量错地方）

| 项 | 记录 |
|---|---|
| 现象 | 打开卡片先转一会儿圈，**每次**都这样 |
| 时长 | 主观"几秒" |
| 看到的东西 | 卡片里的骨架/空白（**不是**我们那张写着「magpie 正在启动…」的等待页） |
| 不是 | Hana 刚启动后的第一次（冷启动）专属现象；他说每次都有 |

"等待页 vs 页内骨架"这个区分很关键：前者说明上游没就绪（我们自己的问题），后者说明页面已经开始了（要么页内慢，要么宿主那层没放行）。

---

## 二、排查方法：三层，先证伪自身

顺序是刻意的：**先证明"不是我这条链路"，再往外走**。理由很实际——如果错在自己的层而先去找别人的问题，会白烧很多时间。

1. **代理层**：同一个请求，比"经代理"和"直连上游"的耗时差 → 代理的固定开销。
2. **页面层**：把时钟埋进页面（`boot` / `dom-ready` / `load` / 首绘 / 最大内容绘 / 长任务），
   让页面自己上报"我什么时候开始、什么时候画完"。
3. **宿主层**：用卡片 URL 里的 surface 票据（里面有 `issuedAt`）当锚点，量"宿主什么时候决定开卡"；
   用进程创建时间排除"每次新建 webview"。

每一层都必须有一个**对照项**。本轮最有用的对照是 `/api/omarchy`：它是唯一不读 magpie 设置的接口，
1ms；而所有慢接口都要读设置 —— 这条对照直接把慢的归属钉到了 `settings.Load()`。

---

## 三、量到的数字

### 1. 代理层（1~10ms，不是它）

| 请求 | 耗时 |
|---|---|
| `/api/update?lang=zh`（走完整条代理链路） | 3ms |
| `/icons/favicon.svg` 等静态资源 | 1~4ms |
| `/`（页面 HTML，含注入） | 8~11ms（仅 App 刚启动那次 68ms） |

### 2. 资源与体积（不是它）

一次卡片加载要拉 **3.1MB**：

| 文件 | 大小 |
|---|---|
| `/i18n.js?v=…` | 1157KB |
| `/app.js?v=…` | 1023KB |
| `/routing.js` / `/library.js` | 233KB / 193KB |
| 其余 CSS/JS/图标 | 合计约 500KB |

代理把这一整套发完用 **约 60ms**；把这 2.6MB 的 JS 丢给本机 node，**解析 27ms、编译 11ms**。
所以"前端太肥导致几秒"这条路也不成立（肥是真的，但代价是几十毫秒级）。

### 3. 接口（原始就是它，已修）

同一时段、同一批接口，缓存前后对照：

| 接口 | 修前 | 修后 |
|---|---|---|
| `/boot.js`（**81 字节**，写在 `<head>` 里阻塞首绘） | 393ms | 1~3ms |
| `/api/library` | **1387ms** | 1~2ms |
| `/api/plugins` | 512ms | 1~2ms |
| `/api/state` | 407ms | 1~2ms |
| `/api/providers` | 393ms | 1~16ms |
| `/api/settings` | 365ms | 1ms |
| `/api/agents/install` | 330ms | 1~2ms |
| `/api/agents/cli` | 314ms | 1~2ms |
| `/api/omarchy`（对照，不读设置） | 1ms | 1ms |

归属：这些慢的是 **magpie 自己**的开销（`settings.Load()` 那条路），而且**与用户数据无关**——
复制一份 `magpie.exe`、用空配置另起一个实例，同样 277~313ms。
App 侧不能改 magpie（项目红线），所以在代理层挡一层（见第五节）。

### 4. 页内时钟（0.2~0.4 秒，很快）

最干净的一次（他发完消息立刻打开卡片那次）：

| 事件 | 时刻 | 相对 |
|---|---|---|
| Hana 签发票据 | 00:03:29.682 | — |
| 页面脚本开始执行（`boot`） | 00:03:29.715 | 票据后 **+33ms** |
| 首绘 / 首内容绘 | — | 导航后 84ms / 88ms |
| 最大内容绘（LCP） | — | 导航后 **180ms** |
| `dom-ready` | 00:03:29.836 | 票据后 +121ms |
| 我们的注入完成（`theme-select-ready`） | 00:03:30.081 | 票据后 **+366ms** |
| 长任务（>50ms） | — | **一条都没有** |

另两次观测：票据→脚本 43ms / 46ms。也就是说**从宿主决定开卡到卡片画完内容约 0.2 秒**。

### 5. 宿主挂载（不是它）

| 检查 | 结果 |
|---|---|
| 票据签发 → 页面脚本执行 | 33~46ms（三次一致） |
| 打开卡片时是否新建 webview 进程 | **没有**（最近的 `msedgewebview2` 是 15:05 起、`HanaAgent` 是 22:11~22:15；卡片是 23:56/00:03 打开的） |
| 他发消息 → 票据签发 | 1.2 秒（**还含他自己点一下的反应时间**） |

### 顺手挖出来的一个真 bug

客户端脚本拼 URL 时会带上宿主的挂载前缀，于是

```
/_hana/diag   →   /api/apps/magpie-hana/routes/_runtime/<rid>/_hana/diag
```

而代理只认"原样以 `/_hana/` 开头"，这些请求全被当普通请求转给上游吃 404。后果有两个：
1. 页面里的诊断探针上报**全部丢失**（所以前一轮 `diag` 一直是空的，我一度误判成"他还没打开过卡片"）；
2. 客户端取主题变量（切换主题后重画要用）也落空。

现在先按服务路径归一化再判断，并把 `req.url` 换回服务内路径。验证：带前缀的 `POST …/_hana/diag` 返回 200、diag 条目 0→1；带前缀的 `GET …/_hana/theme?theme=midnight` 返回 61 个变量（原来 404）。

## 六、还没查清的（诚实边界）

1. **Hana 那层骨架的撤除条件还没找到。** 只在它的 renderer 代码里读到：
   - 一套 `_cardPendingSurface` / `_cardPendingShimmerLayer` / `_cardPendingTitle` 的骨架组件（就是用户看到的转圈壳子）；
   - 一套**服务文档状态机**（`unregistered` / `pending` / `ready` / `stopping` / `unavailable`），挂在 `use-app-service-document-*.js`，带 **15 秒**观察超时（`Oe=15e3`）；
   - 一张就绪登记表（`xn`，写入方 `Bh()`，判定方 `Vg()`）决定清单里的 `domStatus: ready|loading`。
   骨架撤掉走的是这套宿主簿记，**跟"网页加载完没有"不是同一条线**。
2. **只有三次观测**（两次票据+一次对齐）。三次一致，但次数少，不能当成统计结论。
3. 15 秒超时是**读代码读到的**，没实测触发过。
4. 一个反证待补：**换一张别的 App 卡片（Git Save/Load、远程访问）试**，如果同样慢，则这是 Hana 对所有 App 卡片的通用行为。

## 八、教训

1. **"我这条链路变快了"和"他体感变快了"是两件事。** 前两轮我把 `/boot.js` 从 393ms 修到 3ms、`/api/library` 从 1387ms 修到 2ms，数字都真，但体感没变 —— 因为那几秒压根不在我量的那段里。**先问清楚"你看到的是什么"（等待页？骨架？空白？），再决定量哪一段。**
2. **锚点比猜测值钱。** surface 票据里的 `issuedAt` 把"宿主什么时候决定开卡"从黑箱里拿了出来，一次就把 1.2 秒的存在与否钉死了。凡是系统里已经存在的、带时间戳的东西，先找它，别急着埋新点。
3. **埋点失败要当 bug 查。** `diag` 空了一整轮，我先归因成"他还没打开过"，实际是路径前缀把我自己的上报全吃了。空数据先怀疑仪器。
4. **排除也要有量法。** 这轮最有用的三个对照：新实例复现（一次排除全部用户数据）、不读设置的接口（1ms，钉住归属）、进程创建时间（一次排除"每次新建 webview"）。
5. **量到边界就停手，说清楚边界在哪。** 这轮的结论是"Hana 那层盖的骨架"，不是"App 修好了"。把只能靠"看一眼"的部分交给用户，把还没查清的部分单列出来，比继续在本层拧螺丝诚实。

# 追加：第二轮（10-08 深夜 ~ 10-09 凌晨）——卡片改型，以及"5 秒到底在哪"

第一轮结尾写着"剩下在 Hana 那层"。这轮把它拆到了具体的一道门上，改掉了卡片类型，
但那 5 秒**没有消失**。所以这份追加的重点是：已经排除什么、还剩什么、以及为自己的错留痕。

## 一、这轮新量到的（页面侧依旧干净）

| 观察 | 数字 |
|---|---|
| 壳子（route 卡片的薄页面）脚本开始 → 第一个请求 | +36ms / +45ms（两次） |
| 内层页面 boot → 完全就绪（theme-select-ready） | ≈ 330ms |
| 一次加载的资源量 / 代理发完 | 3.1MB / ~100ms |
| 打开卡片时的新建 webview 进程 | 没有（最近的 msedgewebview2 是当天 22:01 起） |
| 打开卡片时的 app 重载 | 没有（最后一次重载比操作早十几分钟） |
| 页面侧长任务（>50ms） | 0 条 |

⇒ App 这一侧（含内嵌）合计约 **0.4 秒**；那几秒落在**卡片文档被创建之前**。

## 二、Hana 的卡片有两种（本轮最关键的结构差异）

| | route 型 | service 型 |
|---|---|---|
| manifest | `"route": "/x.html"` | `"service": {"id","path"}` |
| 文档由谁伺服 | Hana 的 app-host | App 自己的服务（经反代） |
| 例子 | 图库 `ui/panel.html`、token-tracker | magpie-hana（改型前） |
| 打开速度 | 秒开 | 等一道门 |

## 三、那道门是什么（读 Hana 代码读到的）

- 服务端：`if (R.state === "pending") return 409 "the App's managed service is still starting"`；
  挂载时还要复查 `serviceState.state === "ready"`，中途变脸报 `APP_SURFACE_STALE`。
- 渲染端：服务文档观察是一条 NDJSON 流（`/api/app-service-status/events`，**host-only**，
  未授权回 `Only a host owner may observe service status`），状态机
  `unregistered|pending|ready|stopping|unavailable`，`Oe = 15e3` 观察超时，
  而且 `readyOnTimeout: false` —— **超时不算就绪**。
- 宿主与卡片文档之间还有一次"可信握手"：向 iframe 发 `chrome-challenge` / 带 `documentNonce` 的
  chrome 动作请求，等文档在同一协议里回话；等不到就报
  `The App did not answer the chrome action in time.`（超时常量 `Uc = 1e4`）。
  `hana.chrome.set` 的报错文案写得很直白：*available after this App card has completed its trusted handshake*。
  **这次握手只认 Hana 自己签发的文档**，第三方服务伺服的文档永远回不了话 —— 于是每次都等到超时。

## 四、改型（service → route）与它的副作用

- manifest：卡片声明由 `service` 改成 `route: /card.html`；运行时那侧 `service` 注册保留（无害，待清理）。
- 新增 `ui/card.html`：一个薄壳子，两件事 —— 负责握手（Hana 伺服，瞬间完成）、
  拿 App 路由 `/status` 里的 `proxyPort` 把 magpie 界面放进 iframe；
  另外兼一座桥：主题选择的持久化要落到 App 路由（壳子与它同源，iframe 不同源）→ 由壳子代转。
- manifest 新增 `ui.csp.frameDomains = ["http://127.0.0.1","http://localhost"]`：
  Hana 默认策略是 `default-src 'none'` 且不写 `frame-src`（= 继承 `'none'`），不声明就嵌不了内网端口。
  CSP 里 `http://127.0.0.1` 不带端口即匹配任意端口，正好对上"代理端口每次启动随机挑"。
- 副作用：**旧卡片实例会失效**，报 `The App directory no longer declares the service this card was opened with.`
  （实例记着"当初用哪套声明打开的"）；"重试"按钮救不了它，必须删掉再加一张。
- 改型之后：那 5 秒**还在**。

## 五、改型之后，归因收窄到什么程度

页面 0.4 秒、没有新进程、没有重载、代理侧无异常请求、Hana 日志在那 5 秒里是**空白**
（实测：某次打开前 8 秒日志全空，页面却在之后才起来）。

⇒ 只剩两类：

- **A 类 · 实体层**：慢在这个 App 的卡片实体上（旧实例、`trust` 级别、声明形态），与内容无关；
- **B 类 · 内容层**：慢在壳子的两步（取端口 / 内嵌 iframe）。

判定方式：`ui/ping.html` + manifest 里的 `ping` 卡（`cardForm: flush`），内容只有一行字，
不取端口、不内嵌、不发请求。同一个 App 两张卡对照，**一次打开即可分开 A/B**。
**这一步还没做（等一次打开）。**

## 六、旁证：这台机器上 Hana 的慢性负载

`sessions_list_timing`：当天 **335 次、中位 2097ms、最长 45293ms、累计 973 秒**（`sessionCount: 1269`）。
它不是那几次打开的直接原因（实测那会儿它是空闲的），但很可能是"点什么都偏慢"的大背景，值得单独反映。

## 八、我在这轮犯的错（留痕）

1. **把"我这条链路快"当成了"卡片快"。** 改型前页面就 0.4 秒，我却先宣布"剩下在 Hana 那层"，
   接着又把功劳记在改型上 —— 实际上改型之后那 5 秒没变。
2. **悬空引用打断了诊断通道。** 给 boot 探针加了 `shellT0: SHELL_T0`，清理时只删了定义、漏了引用；
   悬空引用在注入脚本早期抛错，页面侧探针一条都没上报。现场看起来像"kind 白名单丢了数据"，
   我先怀疑白名单，最后才回过头 grep 一遍符号。**改注入代码后必须 grep 符号定义。**
3. **把测量变成了用户的工作。** 连着几轮让他"点一下再发消息"、"点两次看快慢"。
   正确做法是先问他想怎么测，或者直接用本机 GUI 工具自己点 —— 而不是让他做仪式。

## 九、对第一轮结论的更正

- 第一轮写"剩下在 Hana 那层"方向对，但没说清是哪一层；本轮把它定位到"卡片挂载 = 服务文档门 + 可信握手"。
- 第一轮把 service 卡的慢归给"服务文档没 ready"；本轮读到 `readyOnTimeout: false` 与可信握手那段代码，
  说明**握手这一层更可能是真正的等待**（去掉服务门之后慢没变）。但**仍未证实**：
  缺"点击 → 卡片文档开始"这一段实测。
- "打开卡片会断对话"要精确化：断的是 **app 被重载**的时候 —— 受管 magpie 跟着重启
  （实测：3425 与上游端口是**同一个 pid**；而每次重载上游端口都换新，说明 magpie 確實换了）。
  **打开卡片本身不会重载 app**（实测：四次打开与十一次重载的时间对不上）。

## 十、当前结论与出路

App 侧 0.4 秒封顶；5 秒在 Hana 的卡片挂载路径里，具体哪一处还差一次对照（Ping 卡）。
出路按代价排：

1. 一次打开，读 Ping 卡 → 分开 A/B 类；
2. 若是 A 类：删掉旧实例重新添加，或检查 `trust` / 声明形态；
3. 若是 B 类：去掉取端口/内嵌那两步，改成走 Hana 路由（中等改动）；
4. 无论哪类，都把这份材料整理成给 Hana 的报告（带上会话列表那笔背景负载）。
